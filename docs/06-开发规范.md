# 06 · 开发规范

> 状态：生效中 ｜ 更新：2026-09-27（并入阶段 0 编码细则）
> 本文件说明"怎么一起干活"：环境、构建、测试、CI、分支、完成标准、许可证合规和发版。

## 1. 开发环境

- macOS 15 或更高的开发机。
- Xcode 26 或更高。首次安装后运行一次 `xcodebuild -runFirstLaunch`，补齐模拟器和设备组件，否则命令行构建时会出现 CoreSimulator 相关的报错。
- Homebrew，以及 XcodeGen：`brew install xcodegen`。
- GitHub CLI：`brew install gh`（发布版本时使用）。
- Node.js 20.12 或更高，以及 uv：BMAD-METHOD 的安装器需要 Node.js，它的技能会通过 `uv run` 执行脚本（见 §8）。

## 2. 获取与构建

```bash
git clone https://github.com/MICBIK/shike.git
cd shike
xcodegen generate                               # 生成 Shike.xcodeproj（不入库，改了 project.yml 就要重新生成）
open Shike.xcodeproj                            # ⌘R 运行，⌘U 运行 App 层测试
swift test --package-path Packages/ShikeKit     # 运行解析与数据层测试，不需要打开 Xcode
```

## 3. 工程约定

- **模块边界：**见 [04 §1](04-技术架构.md#1-总体结构)。ShikeKit 中的代码不得引入 AppKit 或 SwiftUI。
- **语言与警告：**Swift 6 语言模式，严格并发检查；不允许新增编译警告。
- **命名与注释：**代码标识符用英文；注释用中文，重点解释"为什么"。
- **界面文案：**简体中文，集中放在 `Localizable.xcstrings`，不在代码里直接写死。
- **偏好设置：**键名集中定义在 `Preferences.Key`，不在别处直接使用字符串。
- **依赖：**一律锁定精确版本；新增依赖需要在 [07](07-决策记录.md) 记录理由、在 NOTICE 中登记，许可证必须与 GPL-3.0 兼容。
- **入库规则：**`.xcodeproj` 不入库；`Packages/ShikeKit/Package.resolved` 入库；BMAD 的 `_bmad/`、`_bmad-output/`、`.claude/skills/` 入库（BMAD 自带的忽略规则会排除个人覆盖配置 `_bmad/custom/*.user.toml`）。
- **文件头：**每个源文件开头带许可证声明，见 §9。

## 4. 测试

### 4.1 分层

| 层 | 载体 | 运行方式 | 覆盖对象 |
|---|---|---|---|
| L1 | ShikeKit 中的 Swift Testing 测试 | `swift test --package-path Packages/ShikeKit`；CI 必跑 | 中文日期解析（[05](05-中文日期解析规格.md) 用例表每一行）、数据层、领域逻辑 |
| L2 | `ShikeTests` 测试目标 | Xcode 中 ⌘U；CI 必跑 | 偏好设置等可以脱离界面的 App 层逻辑 |
| L3 | 手工验收 | 产品负责人按 [02](02-阶段路线图.md) 的验收清单实测 | 界面、交互、系统集成（通知、开机自启、卡片、更新） |

能用 L1 覆盖的，就不留给 L2 和 L3。

### 4.2 规则

- 修 bug 时，先写一个能复现问题的失败测试，再修复。
- 修改解析规则时，在同一次提交中同时修改 05 的规则说明、用例表和对应测试。
- 新的仓储方法和领域逻辑必须有 L1 测试。
- 测试不依赖真实的当前时间和系统时区：统一传入基准时间，时区固定为 Asia/Shanghai。基准时间 T0 = 2026-09-23（周三）12:00，Asia/Shanghai，通过 `now` 参数或注入的时钟传入；数据库时间戳精度是毫秒，基准取整秒。解析用例以 05 的编号作为参数标识，测试标题用中文描述行为。
- 一般测试用内存库；备份和打开失败的测试用临时目录中的磁盘库，测试结束后删除。
- L2 测试用内存库和独立的 `UserDefaults` 组装 `AppEnvironment`，不打开任何窗口。

## 5. CI

- 配置文件：`.github/workflows/ci.yml`。推送到任何分支、以及发起 PR 时运行；同一分支的新推送会取消还在跑的旧一趟（concurrency 组按分支）。
- 运行环境：GitHub 提供的 `macos-26` 镜像（Apple 芯片），使用镜像默认的 Xcode 26。本地使用更新版本的 Xcode 时，以 CI 能通过为准——两代编译器对并发隔离检查的严格程度有差异（实例：Xcode 27 通过而 Xcode 26 报错的 `#expect` 宏展开，2026-09-27），"本地绿"不能替代 CI 确认。
- 三个作业，作业名固定，分支保护按名称绑定：
  1. **checks**（ubuntu）：架构合规检查（`scripts/checks.sh`，先自检再检查）：①文件头与 NOTICE 登记；②导入边界（ShikeKit 不引 AppKit/SwiftUI；App 不 import GRDB；ShikeData 只用 `internal import GRDB`；解析器只 import Foundation）；③解析器区域（不出现 `Calendar.current` 等系统设置读取）；④禁用项（不出现 `eraseDatabaseOnSchemaChange`、App 中无全局单例）。
  2. **package-tests**（macos-26）：`SHIKE_WARNINGS_AS_ERRORS=YES` 下运行 `swift test --package-path Packages/ShikeKit`（L1）。
  3. **app**（macos-26）：下载 XcodeGen 2.46.0 并以 SHA-256 校验后生成工程，`SHIKE_WARNINGS_AS_ERRORS=YES` 下 `xcodebuild build test`（L2）。
- "警告即错误"只在 CI 开启（ADR-019）：本地默认宽松，新增警告在合并前按 CI 结果处理。
- main 分支保护已开启：要求 checks、package-tests、app 三项通过，要求 1 个审查通过（过时审查自动失效），通过 PR 合并（squash）。

## 6. 分支与提交

- **main 分支**任何时候都能编译、测试全部通过。
- **分支命名：**`stage-N/主题`（如 `stage-0/foundation`）、`fix/主题`、`docs/主题`。
- **合并方式：**通过 PR 合并到 main（squash 合并），CI 必须通过。
- **提交信息：**`类型: 说明`。类型取 `feat`、`fix`、`docs`、`refactor`、`test`、`build`、`ci`、`chore`；说明用中文，一句话讲清楚改了什么。例如：`feat: 快速输入框在输入法组合时不响应回车`。
- **版本标签：**每个阶段完成后在 main 上打标签：`v0.0.0`、`v0.1.0` …… `v1.0.0`；修补版本递增最后一位，如 `v0.1.1`。

## 7. 完成的定义

一项能力（S 编号）只有同时满足以下全部条件，才算完成：

1. 代码已合并到 main，CI 通过。
2. 能自动化测试的部分都有测试。
3. 产品负责人按 02 的验收清单实测通过。
4. 受影响的文档已经同步：02 中的状态、03/04/05 的相关章节、07 中的新决策。
5. 没有新增编译警告。
6. 移植的代码已加文件头，并登记到 NOTICE。

文档里写了"完成"，但不满足上述条件的，不算完成。

## 8. 阶段工作流程

开发流程使用 **BMAD-METHOD**（6.12.0，bmm 模块，见 ADR-016）。每个阶段对应 BMAD 中的一个史诗。在仓库目录中启动 Claude Code，按以下顺序使用 BMAD 技能：

| 步骤 | BMAD 技能 | 产物 | 需要产品负责人确认 |
|---|---|---|---|
| ① 阶段规格 | `bmad-spec` | `_bmad-output/specs/spec-stage-N-主题/SPEC.md`，以 02 中该阶段的能力清单和 docs/ 为输入 | 是 |
| ② 拆分故事 | `bmad-create-epics-and-stories` | `_bmad-output/planning-artifacts/epics-stage-N.md` 中的史诗和故事 | 是 |
| ③ 冲刺计划 | `bmad-sprint-planning` | `_bmad-output/implementation-artifacts/sprint-status.yaml` | 否 |
| ④ 逐个实现 | `bmad-build`（每个故事一次） | 代码和测试，提交在 `stage-N/主题` 分支上 | 否 |
| ⑤ 代码评审 | `bmad-code-review` | 评审结论，以及据此做的修复 | 否 |
| ⑥ 验收 | 人工 | 产品负责人按 02 的验收清单实测，发现的问题记录并修复 | 是 |
| ⑦ 回顾 | `bmad-retrospective` | `_bmad-output/implementation-artifacts/` 中的回顾 | 是 |
| ⑧ 收尾 | — | 合并到 main，打标签，更新 02 中的状态 | — |

- ① 和 ② 经产品负责人确认后，才能进入实现。
- **史诗编号：**阶段 N 对应 Epic N+1，例如阶段 0 是 Epic 1，冲刺状态中的键为 `epic-1`、`1-1-…`。BMAD 6.12.0 的回顾脚本不接受编号 0（已实测）。
- **史诗文件：**拆分故事的技能总是新建 `epics.md`，完成后要改名为 `epics-stage-N.md`，下一阶段拆分时才不会覆盖它。往期的 `epics-stage-*.md` 只读。团队配置 `_bmad/custom/bmad-create-epics-and-stories.toml` 让 AI 自动遵守编号规则，并在完成后改名。
- **实现时加载规格：**bmad-build 汇总史诗上下文时只扫描 `planning-artifacts/`，看不到 `_bmad-output/specs/` 中的阶段规格。团队配置 `_bmad/custom/bmad-build.toml` 让它在为每个故事写实现规格时，把 SPEC.md 和故事引用的伴随文件列入规格的 `context`。
- 不确定下一步做什么时，调用 `bmad-help`。
- docs/ 是 BMAD 的项目知识目录，BMAD 产物由它派生。两者不一致时，先判断哪一边错了，修正后再继续。
- 阶段进行中冒出的新想法，记到 GitHub Issues 并加上 `idea` 标签，不插入当前阶段。
- BMAD 版本锁定为 6.12.0。升级时重新运行安装器，并单独提交一次。

## 10. 发版流程

阶段 0～3 只在 main 上打标签，不发布安装包；从阶段 4 开始发布。

- **版本号：**`MARKETING_VERSION` 使用语义化版本（0.1.0 …… 1.0.0）；`CURRENT_PROJECT_VERSION` 是递增的整数构建号。
- **发布步骤：**
  1. 更新版本号和 CHANGELOG。
  2. 运行 `scripts/release.sh 版本号`：编译 Release → ad-hoc 签名 → 打包 zip 和 dmg → EdDSA 签名 → 更新 appcast → 创建 GitHub Release。
  3. 在一台干净的 Mac 上验证首次安装和从上一版本升级。
- **私钥：**Sparkle 的 EdDSA 私钥只保存在开发者的钥匙串中，并另外备份到密码管理器。私钥一旦丢失，已安装的用户将无法收到自动更新，只能手动重新下载。

## 11. 调试

- **数据目录：**`~/Library/Application Support/Shike/`（数据库和 `Backups/` 都在这里）。
- **模拟数据库打不开：**在 Xcode 的 Scheme → Run → Arguments 中加入 `-ShikeSimulateDatabaseOpenFailure YES`。只有第一次打开会失败，之后可以用"重试"验证恢复。
- **模拟写入失败：**加入 `-ShikeSimulateWriteFailure YES`，所有写操作都会失败，用于验收"保存失败时保留输入"。
- **使用临时数据目录：**加入 `-ShikeDataDirectory /tmp/shike-dev`（必须是绝对路径），数据库和备份都放在这个目录里，不会碰到真实数据。
- **清空偏好设置：**`defaults delete io.github.micbik.shike`。
- **查看日志：**打开"控制台"应用，按 subsystem `io.github.micbik.shike` 过滤。
- 调试参数在 Xcode 的 Scheme → Run → Arguments 中加入（XcodeGen 方案已预置、默认不勾选），格式支持 `-Flag 值` 和 `-Flag=值`；只有旗标没有值时判为无效。验收或调试可能损坏数据的场景时，用 `-ShikeDataDirectory` 指定一个临时目录，不要直接使用产品负责人的真实数据目录。

## 12. 编码细则

以下细则自阶段 0 规格（`conventions.md`）并入，作为 06 的一部分生效；与 06 其他章节重复的部分以本节为准，与规格 `conventions.md` 冲突时以本文为准。

### 12.1 组装与依赖

- `AppEnvironment` 负责组装 AppDatabase、仓储、Preferences、各项服务和界面模型；`AppDelegate` 只负责生命周期，以及用 AppEnvironment 创建界面控制器。
- 不写 `static let shared` / `static var shared`；对象都通过 `init` 注入。移植代码里的单例一律改掉（checks 作业会拦）。
- 接入新服务的步骤见 [04 §11.5](04-技术架构.md#115-新增服务)。

### 12.2 并发

- 见 [04 §8](04-技术架构.md#8-并发模型)。要点：显式 `@MainActor`；不启用"默认 MainActor 隔离"；界面模型在自持的 `Task` 中消费观察流、停止时取消；系统回调只有确定在主线程时才用 `MainActor.assumeIsolated`。

### 12.3 错误

- 仓储只抛出 `ShikeDataError`（[04 §4.2](04-技术架构.md#42-shikedata)）；App 用 `ErrorText` 把原因映射成文案，同时写日志。
- 写入和文件操作的失败不得用 `try?` 丢弃。确实可以忽略时，要在注释里写明为什么可以忽略。
- 捕获错误后不走"降级"路径：不改用内存库，不用空数据或默认值覆盖用户数据（ADR-013）。

### 12.4 偏好设置与调试启动参数

- 偏好键集中在 `Preferences.Key`，名称与 [04 §5.5](04-技术架构.md#55-偏好设置userdefaults) 一致；默认值在同一处注册；新的键随所属能力在对应阶段加入，并同步 04 §5.5。步骤见 [04 §11.2](04-技术架构.md#112-新增偏好键)。
- 调试启动参数定义在 `LaunchOptions`，格式 `-Shike<名称> <值>`，登记到 §11，并在 XcodeGen 方案中预置为默认不勾选。步骤见 [04 §11.6](04-技术架构.md#116-新增调试参数)。
- 验收或调试可能损坏数据的场景时，用 `-ShikeDataDirectory` 指定临时目录，不要直接使用产品负责人的真实数据目录。

### 12.5 移植（GPL）补充

- 移植基线为 demo 提交 `e3c0260a8630381224e80f5f0e0c6700f2e417aa`（2026-09-19），记录在 NOTICE 中。
- 凡是照搬或改写 demo 代码的文件都算移植，只取其中一部分函数也算。
- 移植时要去掉 EventKit 与授权流程、App Store 分支、全局单例和已废弃的 API（例如 `NSApp.activate(ignoringOtherApps:)` 改为 `NSApp.activate()`）；尺寸和文案以 03 为准。步骤见 [04 §11.7](04-技术架构.md#117-移植-demo-文件)。

### 12.6 禁止清单（速查）

- 在 App 中 `import GRDB`；在 ShikeKit 中引入 AppKit 或 SwiftUI；在 ShikeData 中用 `public import GRDB` 或不带修饰的 `import GRDB`。
- 使用 `eraseDatabaseOnSchemaChange`；修改已发布的迁移；数据库打不开时降级处理。
- 在解析器中读取系统的日历或区域设置。
- 把 Swift `Regex` 作为 `static` 常量。它不是 `Sendable`，在 Swift 6 下编译失败（已实测），应改用 `NSRegularExpression`。
- 在 xcodebuild 命令行直接传 `SWIFT_TREAT_WARNINGS_AS_ERRORS=YES`（它会作用到 GRDB 并与其 `-suppress-warnings` 冲突，已实测；见 ADR-019）。
- 用 `try?` 丢弃写入或文件操作的失败；使用全局单例。
