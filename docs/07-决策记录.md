## ADR-001 项目更名为拾刻，迁入新仓库

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧项目 TZMemo 的框架代码只做过语法检查，从未编译通过；文档把这些代码标为"已完成"；项目目录也不在版本控制中。
- **决策：**项目更名为「拾刻 Shike」，仓库为 <https://github.com/MICBIK/shike>，Bundle ID 为 `io.github.micbik.shike`。旧的 TZMemo 目录原样保留、不再修改；旧文档归档到 `docs/archive/`。可复用的中文日期解析引擎在阶段 0 迁入并修复。
- **后果：**旧的里程碑 M1～M6 和旧 ADR-001～009 不再生效，由本文件和 [02-阶段路线图](02-阶段路线图.md) 取代。

## ADR-002 只做 macOS

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧方案规划 iOS 复用 Swift 代码，Windows / Android 使用 Flutter，另建跨平台同步后端（候选为 LeanCloud 或 Supabase）。其中 LeanCloud 已于 2026-01-12 停止新用户注册，并将于 2027-01-12 全面停服。
- **决策：**只做 macOS。iOS、Windows、Android、云同步和账号都移入"以后再说"，不作为现在的设计约束。
- **理由：**产品负责人决定先看 Mac 版的使用情况；多端规划对现在的设计只有约束，没有收益。
- **后果：**解析引擎不再以"移植到 Dart"为设计依据。数据库保留 uuid 等字段，是因为它们现在就有用处（通知标识、卡片恢复、导出），而不是为同步预埋。
- **关联：**取代旧 ADR-002，以及旧 ADR-003 中的远期同步部分。

## ADR-003 最低系统 macOS 15，用 Xcode 26 或更高编译

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧方案设定 macOS 13，但代码中用了 macOS 14 才有的接口，导致编译失败。目前最新系统是 macOS 27（2026 年 9 月发布，仅支持 Apple 芯片），macOS 26 是 Intel Mac 能安装的最后一个版本。
- **决策：**最低支持 macOS 15；使用 Xcode 26 或更高版本编译。
- **理由：**
  1. macOS 15 起 Gatekeeper 的放行流程是统一的，安装说明只需要写一份。
  2. 用新 SDK 编译，系统控件在 macOS 26 和 27 上自动呈现 Liquid Glass 外观，在 15 上自动回退为旧样式。
  3. 拾刻需要的能力都不依赖 macOS 26 独有的接口。
  4. 不把还没升级到 26 的用户挡在门外。
- **后果：**用到 macOS 26 独有接口的地方，必须先判断系统版本；CI 使用 `macos-26` 镜像。

## ADR-004 以 GPL-3.0-only 开源，允许移植 Reminders MenuBar 的代码

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**参考项目 Reminders MenuBar 以 GPL-3.0 发布。旧方案规定"只借鉴思路、不复制代码"，这意味着菜单栏面板、兼容输入法的输入框等细节都要自己重新踩一遍坑。
- **决策：**拾刻以 GPL-3.0-only 发布，允许移植 demo 的代码，并按 [06 §9](06-开发规范.md#9-gpl-合规) 添加文件头、在 NOTICE 中登记。
- **理由：**demo 中经过实际检验的代码（外部点击兜底、防止面板刚关又开、输入法组合态保护、按键缓冲回放）能直接降低风险；拾刻本身免费、开源，GPL 的约束可以接受。选择"only"是因为 demo 没有声明"或更高版本"。
- **后果：**今后任何发行版本都必须同时提供源码，闭源商业化基本不可能。
- **关联：**取代旧文档"GPL 协议提醒"中"只借鉴、不复制"的约定。

## ADR-005 原生 Swift 6；AppKit 管生命周期和窗口，SwiftUI 画视图

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧 ADR-001 选定原生 Swift + SwiftUI + AppKit，理由依然成立：知名的 Mac 菜单栏便签应用都是原生实现，Flutter 没有 NSPopover 的对应物。demo 使用 SwiftUI 的 App 生命周期，为了在菜单栏应用中打开设置窗口，写了 218 行绕路代码。
- **决策：**沿用原生技术栈。应用入口使用 `main.swift` + `AppDelegate`（AppKit 生命周期），不使用 SwiftUI 的 App / Scene；面板、卡片、设置等所有窗口都由 AppKit 管理，窗口内容用 SwiftUI 编写。
- **理由：**不抢焦点的浮动卡片、多窗口、设置窗口前置等行为都需要 AppKit 级别的控制；不用 SwiftUI 的 Settings 场景，就不需要那段绕路代码。
- **后果：**必须自己创建一个不显示的主菜单（包含编辑菜单），否则输入框里的复制、粘贴、撤销快捷键都会失效（见 [04 §6.1](04-技术架构.md#61-应用生命周期与主菜单)）。
- **关联：**沿用旧 ADR-001，补充生命周期的选择。

## ADR-006 数据：SQLite + GRDB 7，采用 v1 表结构

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧表结构有几个问题：
  - UUID 列声明为文本，实际却以二进制写入。
  - 删除只有一个布尔标记，"最近删除"无法按删除时间排序。
  - 待办同时有 dueAt 和 remindAt，却分不清"明天"和"明天 9 点"。
  - 预埋了几个格式没想清楚的字段（color、priority、repeatRule、listTag）。
- **决策：**继续使用 SQLite + GRDB 7，以 DatabasePool（WAL 模式）打开。按 [04 §5](04-技术架构.md#5-数据模型-v1) 建立 v1 表结构：
  - UUID 以小写文本存储。
  - 软删除改用 deletedAt 时间戳。
  - 待办时间用 dueAt 加 dueHasTime 表示，另设 snoozedUntil。
  - 桌面卡片单独建表。
  - 删除所有格式未定型的预埋字段。
- **理由：**现在还没有任何真实数据，调整结构没有成本；GRDB 的数据观察能让面板、卡片和菜单栏计数自动保持一致。
- **后果：**迁移只追加，已发布的迁移永不修改。
- **关联：**修订旧 ADR-003。

## ADR-007 便签与待办分开，面板先切模式再输入

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧 ADR-006 决定便签和待办是两个独立实体。这次评估了三种捕捉方式：用提交键决定类型、识别到日期就自动转为待办、先切换模式再输入。
- **决策：**保持两个独立实体。面板顶部用「便签｜待办」切换模式，模式同时决定输入的类型和列表的内容；在输入框中按 Tab 切换，⌘1 / ⌘2 直达；呼出时进入哪个模式可以设置，默认为上次的模式。
- **理由：**这是产品负责人的选择。模式切换直观，每个模式都能针对自己的内容设计完整的列表。
- **后果：**在便签模式下看不到待办，因此在待办模式的按钮上显示"逾期 + 今天"的数字角标作为补偿。
- **关联：**沿用旧 ADR-006。

## ADR-008 桌面卡片的表现方式全部交给用户选择

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**"钉在桌面"可以是浮在最上层、普通窗口或贴在桌面层；浮在最上层时又可能挡住视线。
- **决策：**层级、自动隐藏、隐藏延迟、隐藏后的不透明度、点击穿透、鼠标靠近时浮现、颜色、字号、所在空间、是否显示在全屏应用之上，全部做成每张卡片单独可设的选项，设置中另外提供新卡片的默认值（见 [03 §10](03-交互设计.md#10-桌面卡片)）。
- **理由：**产品负责人明确要求这些表现方式"支持用户自行选择，不能强行锁定为某种形式"。
- **后果：**卡片的状态较多，需要单独建表保存（ADR-006）；"隐藏时点击穿透、鼠标靠近时浮现"依赖全局鼠标监听，需要在 S3-00 中先行验证。

## ADR-009 中文日期解析继续自研

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧 ADR-007 以"没有成熟的中文方案"和"规则表可以移植到 Dart"为由选择自研。这次评估发现两点：
  - demo 使用的系统自带 NSDataDetector，其实能识别不少中文说法，包括"15:30"。
  - 旧解析器有多处时段换算错误（如"中午一点"被算成凌晨 1 点），而且结果会随系统的区域设置变化。
- **决策：**继续自研。按 [05](05-中文日期解析规格.md) 修复并补齐规则；内部固定使用公历，以周一为一周的第一天。
- **理由：**NSDataDetector 不能指定基准时间，测试结果不稳定；它的行为会随系统版本变化，也无法加入"有两点需要注意"这类歧义规则。自研可以按规格精确控制，并逐条测试。
- **后果：**规则的维护成本由我们自己承担。开发时可以拿 NSDataDetector 做对照，帮助发现漏掉的说法。
- **关联：**修订旧 ADR-007：不再以"移植到 Dart"作为理由。

## ADR-010 提醒使用本地通知，以数据库为准对账

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧 ADR-004 决定使用本地通知、不接入系统"提醒事项"，这一点仍然成立。
- **决策：**使用 UNUserNotificationCenter。在启动、数据变化、跨天、唤醒时，以数据库为准核对系统中已经排好的通知；最多只排最近的 50 条。
- **理由：**对账能保证通知和数据始终一致，不会漏发、也不会重复；限制数量可以避开系统对待发通知的数量上限。
- **后果：**调度中"算出哪些该提醒"的部分写成纯函数，可以完整测试（[04 §6.7](04-技术架构.md#67-提醒调度阶段-2)）。
- **关联：**沿用旧 ADR-004，补充对账机制。

## ADR-011 分发：GitHub Releases + ad-hoc 签名 + Sparkle EdDSA，暂不加入开发者计划

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧 ADR-005 的安装说明是"右键 → 打开"，但从 macOS 15 起，这个方法已经无法绕过 Gatekeeper。
- **决策：**
  - 暂不加入 Apple 开发者计划；安装包使用 ad-hoc 签名。
  - 不启用 App Sandbox 和 Hardened Runtime。
  - 自动更新使用 Sparkle 2 的 EdDSA 签名。
  - 安装说明按 macOS 15 及以上的流程编写：系统设置 → 隐私与安全性 → 仍要打开。
  - 1.0 发布后反响好，再加入开发者计划，届时补上签名和公证。
- **理由：**先不花钱验证产品。不启用沙盒，能简化全局鼠标监听、导出和更新；Hardened Runtime 只在公证时才需要，现在启用没有收益。
- **后果：**每位用户首次打开时需要手动放行一次；ad-hoc 签名与 Sparkle 配合的完整更新链路在 S4-00 中验证。
- **关联：**修订旧 ADR-005。

## ADR-012 工程：XcodeGen、本地包分层、Swift Testing、锁定依赖版本

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧 ADR-008 采用 XcodeGen，理由是改动便于对比，但当时项目并不在 git 中。旧的测试器是一个可执行程序，因为当时机器上没有 Xcode。
- **决策：**
  - 继续使用 XcodeGen，生成的工程文件不入库。
  - 解析和数据层放进本地 Swift 包 ShikeKit，用 `swift test` 运行测试。
  - 测试框架统一为 Swift Testing。
  - 所有依赖锁定精确版本。
- **理由：**本地包让核心逻辑可以脱离 App 快速测试，也从结构上保证界面代码不能直接访问数据库。机器上已经装了 Xcode，不再需要可执行测试器。
- **后果：**克隆仓库后需要先运行 `xcodegen generate`。
- **关联：**沿用并修订旧 ADR-008。

## ADR-013 数据安全：不静默降级，写入失败保留输入，每日备份

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧代码的写操作全部用 `try?` 吞掉错误，而输入框无论保存成功与否都会清空；数据库打不开时悄悄换成内存库，退出后数据全部丢失。这与"不丢数据"的原则直接冲突。
- **决策：**写入失败时告诉用户，并保留输入的内容；数据库打不开时弹出明确的提示；每天自动备份一次，默认保留最近 7 份。
- **理由：**对一个捕捉类应用来说，最不能接受的就是用户以为记下了，实际却丢了。
- **后果：**界面需要提供错误提示条；备份会占用少量磁盘空间。

## ADR-014 流程：计划先行，确认后动手，"完成"以 CI 和实测为准

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧 ADR-009 建立了确认制，但旧文档依然把只做过语法检查的代码标成了"完成"。
- **决策：**保留"计划 → 确认 → 实现 → 验收"的流程（[06 §8](06-开发规范.md#8-阶段工作流程)）；是否完成按 [06 §7](06-开发规范.md#7-完成的定义) 判断；代码和文档不一致时，以验证过的事实为准，修正出错的一方。
- **理由：**文档只有和可验证的事实挂钩，才值得信任。
- **后果：**每个阶段都要经过 CI 和人工验收两道关。
- **关联：**沿用并修订旧 ADR-009。

## ADR-015 全局快捷键使用 KeyboardShortcuts，默认开启

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**旧方案没有在 KeyboardShortcuts 和自己封装系统热键接口之间做出选择。demo 使用 KeyboardShortcuts，快捷键默认关闭。
- **决策：**使用 KeyboardShortcuts（MIT）；快捷键默认开启，默认组合 ⌃⌥N，在阶段 1 实测确认没有冲突后定稿。
- **理由：**这个库成熟，自带录制快捷键的控件，基于系统热键接口实现，不需要辅助功能权限。快捷键是"3 秒捕捉"的核心，应当开箱即用。
- **后果：**多一个依赖（MIT 许可，与 GPL 兼容）。
- **补记（2026-09-29）：**产品负责人反馈三键组合不趁手，倾向两键，要求重新考虑默认组合（自定义需求本身由 Recorder 覆盖：设置 → 快捷键，本阶段已实现）。候选新默认 **⌥N**：保留 N 助记；不是系统级快捷键；ABC 布局下 ⌥N 是 ˜ 死键，仅影响输入欧洲变音字符，拼音输入不受影响。备选里 ⌥空格与 Raycast/Alfred 冲突，⌃空格是输入源切换，⌘N / ⌘⇧N 与系统"新建"冲突。
- **补记二（2026-09-29，定稿）：**默认组合定为 **⌥N** 并随视觉打磨批次实施。KeyboardShortcuts 的 `initial:` 只在首次启动写入 defaults，存量安装由 AppDelegate 启动时一次性迁移（存储值恰为旧默认 ⌃⌥N 才改写，用户自录或清空的不动）。

## ADR-016 采用 BMAD-METHOD 作为开发流程

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**文档阶段用的是另一套 AI 工作流插件（superpowers），原计划把每个阶段的实施计划写在 `docs/plans/`。产品负责人决定不再使用该插件（已在本机卸载），改用 BMAD-METHOD。
- **决策：**
  - 在仓库中安装 BMAD-METHOD 6.12.0 的 bmm 模块并对接 Claude Code：技能放在 `.claude/skills/`，框架和配置放在 `_bmad/`。
  - 交流语言和文档语言均为简体中文。
  - `docs/` 作为 BMAD 的项目知识目录；BMAD 的产物放在 `_bmad-output/`。
  - 每个阶段按 [06 §8](06-开发规范.md#8-阶段工作流程) 的顺序推进：阶段规格 → 拆分故事 → 冲刺计划 → 逐个实现 → 代码评审 → 验收 → 回顾。
  - BMAD 的所有文件都入库（个人覆盖配置除外），版本锁定为 6.12.0。
- **理由：**这是产品负责人的指定。拾刻已经有完整的产品、交互、架构文档，BMAD 对这种情况的建议正是跳过规划类技能、直接从每个史诗的规格开始，与现有文档衔接自然。
- **后果：**
  - 开发环境需要 Node.js 20.12 以上和 uv。
  - 取消 `docs/plans/`，实施计划改由 BMAD 的规格、故事和冲刺状态承载。
  - ADR-014 的原则不变："计划 → 确认 → 实现 → 验收"，"完成"以 CI 和实测为准，只是载体换成了 BMAD。
- **关联：**修订 ADR-014 中实施计划的形式。

## ADR-017 updatedAt 只随内容变化更新

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**04 §5.1 原先规定"所有写操作同时更新 updatedAt"。但便签列表按"最近修改"排序，并显示修改时间（S1-05）；阶段 1 的验收又要求撤销删除后"内容和位置不变"。如果删除、恢复、置顶也更新 updatedAt，撤销后的便签会跳到列表最前面，修改时间也会变成"刚刚"。
- **决策：**`updatedAt` 表示内容最近一次被修改的时间，在以下变化时更新：便签的内容；待办的标题、时间、完成状态和稍后提醒；卡片的任何字段。软删除、恢复，以及便签的置顶和取消置顶，都不更新它。
- **理由：**列表中的"修改时间"和排序应当反映用户对内容的修改，而删除、恢复、置顶都不是对内容的修改。
- **后果：**修订 04 §5.1。ShikeData 为每个写操作写明是否更新 updatedAt，并逐条测试。
- **关联：**阶段 0 规格（`_bmad-output/specs/spec-stage-0-foundation/`）。

## ADR-018 执行新迁移前先备份

- **日期 / 状态：**2026-09-25 / 生效
- **背景：**迁移只追加（ADR-006），但新迁移本身也可能有缺陷。启动时迁移先于每日备份执行，如果迁移出错，上次备份之后记录的内容就无法找回。产品负责人从阶段 1 起用拾刻记录真实内容。
- **决策：**打开已有的数据库、并且有待执行的迁移时，先在 `Backups/` 中生成 `shike-before-<迁移标识>-YYYY-MM-DD.sqlite`。这类文件不参与每日轮换，也不会被自动删除。备份失败时不执行迁移，按"数据库打不开"处理（04 §6.6）。新建的空库不做这种备份。
- **理由：**迁移是唯一会批量改写已有数据的操作，值得用一份迁移前的完整副本兜底。
- **后果：**带有新迁移的版本在首次启动时会多做一次备份，占用少量磁盘空间。阶段 0 用测试专用的迁移验证这一机制，从阶段 2 出现第二个迁移起实际生效。
- **关联：**补充 ADR-013 的数据安全措施。

## ADR-019 "警告即错误"只在 CI 开启，经环境变量传递

- **日期 / 状态：**2026-09-27 / 生效
- **背景：**要求"不允许新增编译警告"，但开启方式有两个坑：在 xcodebuild 命令行直接传 `SWIFT_TREAT_WARNINGS_AS_ERRORS=YES` 会作用到依赖 GRDB，与其包配置的 `-suppress-warnings` 冲突，报错 `Conflicting options '-warnings-as-errors' and '-suppress-warnings'`（已实测）。同时本地 Xcode（27.0）比 CI 镜像（`macos-26` 默认的 Xcode 26）新，更新的编译器可能带来 CI 上没有的新弃用警告，本地强制会阻塞开发。
- **决策：**CI 的 package-tests 和 app 两个作业设置环境变量 `SHIKE_WARNINGS_AS_ERRORS=YES`：工程目标经 `$(SHIKE_WARNINGS_AS_ERRORS:default=NO)` 读取，ShikeKit 包经环境变量读取并给自身目标加 `.treatAllWarnings(as: .error)`。本地默认宽松；新增的警告在合并前按 CI 结果处理。
- **理由：**既保证合入 main 的代码零警告（GRDB 的警告不被误伤），又不因本地编译器更新而卡住开发。
- **后果：**新增警告只会在 CI 暴露，"本地绿"不能替代 CI 确认；两代编译器对并发隔离检查的严格程度也有差异（实例：`#expect` 宏展开中引用 View 推断的 `@MainActor` 静态成员，Xcode 26 报错而 Xcode 27 通过，2026-09-27 CI 实例），引用此类成员的测试套件应显式标注 `@MainActor`。
- **关联：**补充 [06 §5](06-开发规范.md#5-ci) 与 ADR-003 的"以 CI 为准"。

## ADR-020 ShikeData 公开类型与内部 Record 分离

- **日期 / 状态：**2026-09-27 / 生效
- **背景：**ShikeData 对 GRDB 使用 `internal import GRDB`（导入边界检查要求，防止 GRDB 类型泄漏进公开 API）。实测发现：公开类型不能遵循从 `internal import` 引入的协议（编译报错），因此公开模型无法直接实现 GRDB 的 `FetchableRecord`/`EncodableRecord`。另外 uuid 必须以小写文本存储——GRDB 的编码策略须通过 Record 的 `databaseUUIDEncodingStrategy(for:)` 指定，且必须是**静态函数**；误写成静态属性会被 GRDB 静默忽略，uuid 退回 16 字节 BLOB，正是旧 ADR-006 记录过的缺陷。
- **决策：**公开模型（`Domain/`）与内部 Record（`Records/`）按表一一分离：公开类型是 `Sendable` 值类型、不出现任何 GRDB 类型；Record 类型负责编解码并桥接到公开模型，`databaseUUIDEncodingStrategy(for:)` 写成静态函数返回 `.lowercaseString`。以 `typeof(uuid) = 'text'` 的测试兜底。
- **理由：**在满足导入边界的同时保持公开 API 干净；两个类型的转换是纯映射，成本低。
- **后果：**每张表有两个类型，新增字段时两处都要改；Record 是实现细节，改名或重构不影响使用方。
- **关联：**落实 [04 §4.2](04-技术架构.md#42-shikedata)；uuid 编码要求源自 ADR-006。

## ADR-021 全局快捷键激活改走 CGEventTap 兜底通道

- **日期 / 状态：**2026-09-28 / 生效
- **背景：**阶段 1 验收发现 ⌃⌥N 全局快捷键在真实按键下无响应。lldb 断点证实 KeyboardShortcuts 3.1.0 的注册链完整执行且 `RegisterEventHotKey` 返回成功，但回调永不触发；独立 CLI 复现同样现象，社区亦有记录（macOS 26 起 Carbon 热键回调失灵，voiceTyper 等项目因此迁移）。本机系统为 darwin 27，3.1.0 是当时最新版本、无上游修复。
- **决策：**录制与存储仍由 KeyboardShortcuts 承担（Recorder 控件、defaults 存储、启用开关）；激活机制新增 `HotkeyEventTap`（`cghidEventTap` + `defaultTap` 的 CGEventTap），命中组合即消费按键并执行动作。Carbon 注册保留不动，两条通道共用 `dispatchHotkeyAction`，150ms 内的重复触发折叠为一次——未来 Carbon 若恢复，同一次按键只会执行一次动作。
- **补充（2026-09-29 实测）：**动作必须在 tap 回调返回后的下一拍执行（`DispatchQueue.main.async`）——在回调内同步 `NSPopover.show` 静默失败（tap 消费了按键但面板不出现，用"尾随观察 tap + 系统日志"定位）。另两项配套：辅助功能授权变更需重启进程生效（运行中的进程读不到新授权）；本地 ad-hoc 签名重建后授权失效，`tccutil reset Accessibility <bundleId>` + 重启 + 重新授权可恢复。
- **理由：**CGEventTap 是当前可靠的全局按键通道；保留 KeyboardShortcuts 是因为它解决的是另一件事（组合录制与持久化），换掉它反而要重做录制 UI。修饰键匹配只比较 ⌃⌥⌘⇧ 四位：系统会在事件上附加 SecondaryFn（0x2000_0000）等额外位，无法按"减去已知位"的方式容错。
- **后果：**`defaultTap` 需要"辅助功能"授权：未授权时弹出系统提示、设置页显示说明，授权后在设置页或下次启动自动重试。本地 ad-hoc 签名下授权与具体构建绑定，重新构建需重新授权；正式签名的发布构建不受影响。tap 回调挂在主 RunLoop，命中路径与点击图标完全一致。
- **关联：**ADR-015（引入 KeyboardShortcuts）；排查与验证记录见 `_bmad-output/implementation-artifacts/spec-2-2-全局快捷键.md` 的 Post-Story Fix Log。

## ADR-023 双界面分工：面板保持全部能力，主窗口只做增量

- **日期 / 状态：**2026-09-29 / 生效
- **背景：**阶段 1/2 验收时产品负责人提出：菜单栏弹窗之外，应有完整的应用界面承载全部产品能力。讨论中确立了两个界面的关系——不是"能力在两边二选一"，而是"同一产品能力的两个界面"。曾考虑"面板瘦身为主窗口让路"，被产品负责人否定。
- **决策：**

- **理由：**砍掉已开发已验收的面板能力是纯损失（返工 + 重新验收 + 丢失"不动面板就能完成日常操作"的价值）；主窗口反正躲不掉——S4-05/06/07（回收站、导出、备份）天生需要窗口承载。
- **后果：**docs/02 新增阶段 3.5；S3.5-06 提前实现 S4-06 的导出，阶段 4 只余备份设置；面板零改动、零迁移。

## ADR-024 视觉材质路线：原生厚材质为基调，主题系统降级为"材质档位"

- **日期 / 状态：**2026-09-29 / 生效
- **背景：**可读性修复曾把面板背景换成 93% 实心底，文字清晰了但产品负责人反馈丢了"Mac 的玻璃感"，并提出三个方向：完全个性化、完全原生、主题系统（内置几套、未来用户自定义）。
- **决策：**
  - **基调"原生为主、品牌点缀"**：面板背景改用系统厚材质（`.thickMaterial`）——保留磨砂深度与深浅色自适应，同时对比度足够；"Mac 感"来自系统材质 + 原生控件 + SF Symbols 的正确使用，不等于高透明。

## ADR-025 桌面卡片窗口技术选型（S3-00 技术验证结论）

- **日期 / 状态：**2026-09-29 / 生效（结构验证完成；标注 L3 的三项留真机复核）
- **背景：**阶段 3 动工前需验证四项窗口技术假设（SPEC CAP-1）。验证方式：独立原型 `Prototypes/CardPrototype/main.swift`（swiftc 直编的 accessory 小进程，不依赖拾刻工程与数据目录），脚本化采集证据 + 全屏截屏目视，证据行见同目录运行输出（本机 darwin 27）。
- **结论：**
  1. **唤回监听选定时钟轮询**：`NSEvent.mouseLocation` 单次读取实测 0.023 µs，30 Hz 常驻折合 0.001 ms/s（100k 次采样），零权限、零 TCC；`addGlobalMonitorForEvents(.mouseMoved)` 无 TCC 也能安装（installed=true），但投递需真实鼠标移动、本轮无人动鼠标计数为 0，不作为唯一通道。自动隐藏唤回用 10–30 Hz 共享单定时器轮询鼠标位置并分发命中（NFR25），L3 真机复核投递手感。
  2. **三档层级全部可设**：`floating`(3)/`normal`(0)/desktop(`CGWindowLevelForKey`，key=2，实测值 -2147483623) 均设置并回读成功；截屏目视：floating 压在所有应用窗口之上、normal 被其他应用窗口遮挡、desktop 沉到全部窗口之下——与 03 §10.3 语义一致。桌面层用 `CGWindowLevelKey(rawValue: 2)`（kCGDesktopWindowLevel 宏在 Swift 不可见）。
  3. **空间行为标志回读成立**：`canJoinAllSpaces`/`moveToActiveSpace`/`fullScreenAuxiliary` 及组合均接受；多空间跟随与全屏压盖的真实表现属窗口系统行为，L3 按 02 验收清单复核。
  4. **编辑焦点走"子类化非激活面板"**：borderless `NSWindow` 与默认 `NSPanel(.nonactivatingPanel)` 的 `makeKey` 都拿不到 key（isKey=false / canBecomeKey=false）；**子类覆写 `canBecomeKey=true` 的 `NSPanel(.borderless, .nonactivatingPanel)` 实测 isKey=true 且 firstResponder=NSTextView、可插入文字**——这是"点击不把拾刻变前台、但仍能输入"的标准路线。真机双击 + 中文 IME 的最后一环 L3 复核。
  5. **隐藏穿透参数**：`alphaValue=0.2` + `ignoresMouseEvents=true` 即"看不见但完全不挡操作"，设置即生效（隐藏不透明度 0% 的验收路径同一机制）。
- **决策：**卡片窗口 = `NSPanel` 子类（borderless + nonactivatingPanel + canBecomeKey 按编辑态覆写）；层级三档按结论 2 映射；唤回 = 共享轮询定时器（10–30 Hz）+ 命中分发，全局 mouseMoved 监听作为可选补充；隐藏 = alphaValue + ignoresMouseEvents。原型代码直接演化为 S3-01 骨架。
- **理由：**轮询的成本实测可忽略且零权限（TCC 一律由用户亲手授予的约束下尤其重要）；nonactivatingPanel 是 macOS 长期支持的"不抢焦点面板"官方形态，比"激活应用再还回去"的补丁少一整类焦点回归。
- **后果：**S3-01 起按本选型实现；`stickyCard` 无需加列；ADR 记录的三个 L3 项（唤回手感、多空间/全屏矩阵、双击 IME）并入阶段 3 真机验收清单。
- **关联：**SPEC-stage-3-cards CAP-1；ADR-021（TCC 授权约束）；docs/03 §10、docs/04 §5.4。

## ADR-026 桌面卡片交互修复：desktopIcon 层 + 常驻工具栏（真机验收否决后的重做）

- **日期 / 状态：**2026-09-29 / 生效（真机复核项并入阶段 3 验收清单）
- **背景：**阶段 3 真机预验收被否决（"贴在桌面层之后完全没法点击，卡片上连取消都点不了……非常反人类"）。定位出三处叠加根因：
  1. **桌面层级取错**：用了 desktopWindow 层（key=2，实测 -2147483623，壁纸层）。覆盖整屏的 Finder 桌面窗口在更高的 desktopIcon 层（比壁纸层高 20）——窗口服务器把点击路由给"光标下可收事件的最高层窗口"，desktopWindow 层的任何窗口点击必然落进 Finder（Electron 官方文档同结论："desktop window will not receive focus, keyboard or mouse events"）。S3-00 原型只目视了"沉到全部窗口之下"就判了"与 §10.3 语义一致"——**没验证点击投递，"看得见"被当成了"点得着"**。
  2. **工具栏依赖悬停**：顶部操作条是悬停浮现的覆盖层，正文顶部留白在 10↔26 pt 间跳动；功能性按钮全部要悬停才出现、才可点。任何 hover 链路不灵（低层级窗口、自动隐藏穿透态、跟踪丢失），用户看到的就是"什么都点不了"。
  3. **常用功能入口弱 + 承诺未兑现**：编辑只有双击（不可见）和 ⋯ 菜单；§10.2 承诺的"拖边缘或角调整大小"没有实现（`clampedResize` 无调用方）。
- **同类参照：**桌面小组件类没有一个可交互应用停在 desktopWindow 层：Übersicht 非交互 widget 就在这层并显式 `ignoresMouseEvents`（明知收不到事件），交互 widget 反而临时升到 normal−1；Tack（SwiftUI 便签，与拾刻同构）贴桌模式取 **desktopIconWindow + 1**；macterm 桌面组件取 **+2** 并把"可驻留区间"定义为 (desktopIconWindow, normalWindow)。原值也不行——与 Finder 桌面同层，层内 z 序取决于 orderFront 先后，不可预期。便签类（Windows 11 Sticky Notes、macOS Stickies、Tack）通行范式是**常驻细工具条**（占布局高度，正文从其下方开始）+ 高频动作放顶层按钮（编辑/颜色/层级/关闭）、低频动作进溢出菜单；✕ 只隐藏不删、静默自动保存是三家共同约定。调研全文与 14 个来源见 `_bmad-output/交互修复-2026-09-29.md`。
- **决策：**
  1. 桌面层级改取 `CGWindowLevelForKey(.desktopIconWindow) + 1`（壁纸之上、桌面图标之上、仍低于普通窗口）。副作用：卡片会挡住其正下方桌面图标的点击——同类产品同样如此，拖开卡片即可。
  2. 顶部工具栏**常驻**：永远占位（正文固定从其下方 2 pt 开始，显示/隐藏、悬停与否都不遮挡、不跳动）、永远可点；悬停只把按钮组从 55% 提亮到 100%。
  3. 常用功能上栏：编辑（铅笔/✓ 随编辑态切换）、颜色（按钮即当前色板）、层级（菜单显式三选，图标随层级变化）；⋯ 保留字号/空间/全屏压盖/自动隐藏/在面板中显示/取消钉住。层级"循环按钮"下线——循环方向不可见、不可预期。正文右键 = ⋯ 菜单同源（工具栏之外的第二条通路）。
  4. 右下角调整大小把手补齐 §10.2：拖拽实时钳制最小 160×100，松手按可见区域钳制并持久化（复用 onMove 写路径）。
  5. 换层级后 `orderFrontRegardless()` 重排 z 序（仅窗口可见时）——避免桌面层切回普通层沉到其他应用窗口后面，也保证"隐藏所有卡片"期间观察流回流不复活已收起的卡片。
  6. 防御性配套：`collectionBehavior` 补 `.stationary`（全空间跟随不随切换移动）与 `.ignoresCycle`（不进 ⌘` 窗口循环）；宿主视图 `CardHostingView` 覆写 `acceptsFirstMouse` 兜底非激活窗口 SwiftUI 按钮首击被吞的历史问题（≤macOS 14）。
- **理由：**工具栏常驻把"能不能操作"从 hover 链路的正确性上彻底解耦——桌面层、穿透态、跟踪丢失下所有功能仍然可达；desktopIcon+1 是同类产品长期验证的既可见又可点的桌面层级。
- **后果：**`CardManager.Actions.cycleLevel` / `CardTheme.nextLevel` 删除；docs/03 §10.1/§10.2/§10.3/§10.5 同步修订；真机验收清单新增"桌面层卡片可直接点工具栏各按钮、右下角拖拽调整大小、层级切换后 z 序正确"三项。遗留已知项：SwiftUI Menu 无打开回调，⋯ 菜单展开期间不置 busy（§10.4"菜单打开不隐藏"靠指针在卡内覆盖，子菜单伸出卡外且久停时仍可能淡出）——待 ⋯ 换原生 NSMenu 时一并解决（阶段 3 遗留清单）。
- **关联：**ADR-025 结论 2（层级目视验证不充分，本 ADR 修正其结论）；docs/03 §10；epics-stage-3 4.11/4.12。

## ADR-027 卡片 frame 数据流单向化：窗口层是唯一作者（拖动后弹回初始位置修复）

- **日期 / 状态：**2026-09-29 / 生效
- **背景：**用户真机反馈"卡片拖到新位置后，但凡改颜色或其他选项，卡片弹回屏幕居中的初始位置"。排查：仓储层 `updateFrame`/`updateOptions` 各写各列互不覆盖（回归测试锁定该契约）；记录映射、观察流重读均为最新值。真正机制在窗口层——`controller.apply` 把观察流快照里的 frame `setFrame` 回窗口，而拖动的落库是异步写：**任何其他写库（改选项正是）在拖动写提交前触发观察流回流，旧 frame 就把刚拖的位置弹回去**。而 DB 里 frame 的写入者本来就只有窗口层自己（拖动/调整大小/屏幕变化钳制），观察流回写窗口是一条只带竞态、不带信息的冗余反馈通路。
- **决策：**frame 单向写（ADR-027）：`controller.apply` 不再回写窗口位置，DB frame 只在创建控制器时消费；位移持久化收敛于 `dragEnded`/`resizeEnded`，`windowDidMove` 作兜底（覆盖手势收尾丢失的极端情况），`lastPersistedFrame` 去重避免重复写。
- **理由：**消除"旧快照弹回窗口"的整类竞态，而不是给竞态窗口打补丁；兜底持久化保证拖动位置最终一致。
- **后果：**PinCardFlowTests 新增"移动与改选项互不覆盖"回归；真机验收新增"拖动后改颜色/字号/层级，卡片原地不动"一项。
- **关联：**ADR-026；docs/03 §10.2。

## ADR-028 层级语义修正：普通层级就是普通（不强行提最前）+ 拖动写库风暴修复

- **日期 / 状态：**2026-09-29 / 生效
- **背景：**用户真机反馈"层级不管选悬浮、普通还是桌面，卡片都在顶层——选了普通窗口，卡片还压在浏览器上，和浮在最上层一样"。根因是 ADR-026 决策 5 的误判修复：当时观察到"从桌面层切回普通层，卡片沉到其他应用窗口后面"，以为是 bug 加了"换层级后 `orderFrontRegardless` 重排 z 序"。**那本来就是普通层级的正确语义**（03 §10.3："普通窗口：和其他窗口一样会被遮挡"）。加了它之后，每次观察流回流（改选项/改内容/位移落库）都把卡片提到当前层级最前——普通层级形同置顶，三档层级里"普通"失效。
- **决策：**
  1. `apply(options:)` 只设 level 与 collectionBehavior——level setter 自动把窗口挪到新层级的正确位置；删除 `orderFrontRegardless` 调用。普通层级被遮挡是规格行为；用户要卡片回到眼前：点菜单栏把它所在窗口切走、或切换层级/空间。`show()`（新建/启动恢复/全部显示）保留 orderFrontRegardless——用户主动让卡片出现时提到最前是合理反馈。
  2. 顺带修拖动写库风暴：`windowDidMove` 兜底在 performDrag 拖动过程中会连续触发（每次移动都发），此前每次移动都写库；现拖动/调整大小进行中（isDragging）跳过，收尾路径（dragEnded/resizeEnded）已统一落库。
- **理由：**层级的语义就是 z 序契约——"普通"必须能被遮挡，否则三档塌成两档；兜底落库的职责是"收尾不丢"，不是"每步都记"。
- **后果：**CardGeometryTests 新增层级映射断言（floating > normal；normal=0；desktop 在 normal 之下、desktopIcon 之上）；真机验收新增"普通层级卡片会被浏览器遮挡、切回悬浮即浮出"一项。
- **关联：**ADR-026 决策 5（本 ADR 修正）；ADR-027；docs/03 §10.3。

## ADR-029 普通层级的完整语义：切换即让位、点击浮到前面（原型取证后修正 ADR-028 的不彻底）

- **日期 / 状态：**2026-09-29 / 生效（真机复核项：切层级让位、点击浮出）
- **背景：**用户在 ADR-028 修复后的构建上仍报"普通层级压在浏览器上"。用 LevelProbe 原型（Prototypes/LevelProbe，swiftc 直编 + CGWindowList 取证）做了矩阵实验：同层（normal）下，无论 collectionBehavior 组合（joinAllSpaces+stationary+noCycle / 空 / moveToActive），激活的普通 app 窗口都能正常压住 nonactivatingPanel（v4 三跑稳定）——**z 序机制本身正常，原型无法复现**。真实机制：level setter 把窗口放到新层**最前**——切到"普通"的瞬间卡片正好压在用户正在用的窗口上；用户不重新激活那个窗口就一直"看起来置顶"。ADR-028 只删对了强提，没解决"切层级即压住当前窗口"。
- **决策（按 03 §10.3 的完整语义："和其他窗口一样会被遮挡，点击后浮到前面"）：**
  1. 切到"普通"层级时 `orderBack` 让位：沉到普通窗口链底部，立即不再压住任何正在用的窗口（桌面未被遮住的部分仍可见）。
  2. 点击卡片可见部分 → `orderFront` 浮到普通层最前（CardHostingView.mouseDown）；其他窗口激活时被正常压回（机制已实证）。
  3. 启动恢复的普通层级卡片同样让位（CardManager 恢复首帧标记）；用户主动钉出的新卡仍提到最前（刚操作完要看到它）。
  4. floating / desktop 层级行为不变（level setter 自动浮出/沉底）。
- **理由：**"普通窗口"不是"层级数值 0"而是完整的行为契约——让位时机（切换/恢复时）与回归通道（点击）都要有；否则三档在用户眼里塌成两档。
- **后果：**真机验收更新为："切普通后卡片立即让位（桌面可见部分仍在）→ 点击可见部分浮到前面 → 激活浏览器又压回去"三步闭环。
- **关联：**ADR-028（本 ADR 补完其语义）；ADR-026；docs/03 §10.3；Prototypes/LevelProbe（取证脚本）。

## ADR-030 普通层级强制留在所属空间（跨空间跟随与"会被遮挡"不兼容——用户三指滑动复现定案）

- **日期 / 状态：**2026-09-29 / 生效
- **背景：**ADR-029 构建上用户仍报"普通层级挡住浏览器"，并给出决定性复现路径：**"三指滑动切到别的空间后，普通卡片依旧置顶"**。卡片默认"所有空间跟随"（`canJoinAllSpaces`），跨空间窗口切到哪个空间都跟过去，且在目标空间里压住该空间的窗口——用户看到的就是"置顶"。此前三轮修复（ADR-026/028/029）都在修 z 序，而**问题不在 z 序，在"跨空间存在"本身**：LevelProbe 原型的全部矩阵实验都是单空间的，所以永远复现不了。
- **决策：**`collectionBehavior` 按 level 区分——普通层级**强制 `moveToActiveSpace`**（忽略"所有空间"选项，固定只在钉出/所在的空间显示）；置顶/桌面层保留跨空间跟随（+`.stationary`，它们压不住人或本就该出现在每块桌面）。全屏压盖开关、`.ignoresCycle` 不变。
- **理由：**"属于某个空间的普通窗口"才可能被那个空间的窗口正常遮挡；"出现在所有空间的窗口"在窗口系统里必然压在空间内容之上。两者只能选一——"普通"档选后者即语义失效。同类产品不存在"跨空间 + 普通层级"的实现（Übersicht 交互 widget normal−1 单空间、Tack 贴桌跨空间但那是桌面层）。
- **后果：**CardGeometryTests 锁定按 level 的空间行为；docs/03 §10.3 注明普通层级固定单空间；"空间"菜单项对普通层级卡片的"所有空间"选择不生效（UI 上保留设置值，切回置顶/桌面层即恢复跟随）。
- **关联：**ADR-029（让位+点击浮前语义保留）；ADR-026；docs/03 §10.3；用户三指滑动复现（2026-09-29）。

## ADR-031 普通层级取 normal−1（Übersicht 配方）：编辑即顶到层内最前是"挡人"的最后通路

- **日期 / 状态：**2026-09-29 / 生效（真机复核项：编辑后、切空间后卡片都在其他窗口之下）
- **背景：**ADR-030 修复空间归属后，同类产品调研（Übersicht 源码与 commit 考古、akiflow electron-panel-window、Cindori floating panel 教程、philz.blog NSPanel 逆向）给出关键结论：**可成为 key 的非激活面板放在 normal 层，一旦 makeKey（编辑开始）就会顶到层内最前、盖住其他 app 的普通窗口，且切空间时带着该位置走**——这正是 ADR-026/028/029 三轮 z 序修复全部被真机打回的最后通路（用户的测试流程都在编辑卡片内容）。调研同时确认：nonactivatingPanel/accessory 本身没有 z 序特权，"非激活浮层"业界一律用 floating 层；要在普通窗口之下又可点击可编辑，验证过的取值是 **normal−1**（Übersicht 交互 widget 生产配置，作者为修 Issue #217"同层挡人"降 1 层）。
- **决策：**
  1. 普通层级 `windowLevel = normal−1`：从构造上保证卡片永远在其他 app 普通窗口（normal=0）之下——无论 makeKey、orderFront 多少次都压不过浏览器。仍可点击、可编辑（key 经 CPS steal focus，-1 层不碍事）。
  2. 编辑时临时浮出：beginEditing 置 `level = .floating`（输入可见），endEditing 按 model.options 回落（普通 → normal−1 并 orderBack 让位）。
  3. 编辑中冻结窗口层级/空间属性：controller.apply 不调 panel.apply（颜色/字号由 SwiftUI 随 model 即时渲染），编辑期间用户改的层级选项在 endEditing 统一生效。
  4. ADR-029 的"点击可见部分浮前"保留——在 normal−1 层内提到最前，仍不越界到普通窗口之上。
- **理由：**"不抢焦点"与"普通窗口互遮挡"在 normal 层不可兼得（makeKey 必然顶前）；normal−1 是业界唯一生产验证过的"既不抢焦点、又构造性不挡人"的层位。
- **后果：**windowLevelMapping 测试断言更新（normal == −1；桌面层 < 普通层 < 0 < floating）；docs/03 §10.3 的"普通窗口"表现补注"实际处于普通窗口之下一档"。三档语义最终形态：**置顶=每空间都压一切；普通=单空间、所有普通窗口之下、点击可在层内浮前；桌面=每空间壁纸之上**。
- **关联：**ADR-030（空间归属）；ADR-029；ADR-026；同类产品调研（_bmad-output/交互修复-2026-09-29.md 补记 5）；docs/03 §10.3。
