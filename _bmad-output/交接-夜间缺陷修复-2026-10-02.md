## 2. 卡A · C3/C4 数据安全修复

两个缺陷均为打磨二轮终审记录在案的既有问题（`_bmad-output/审查审计-打磨二轮-2026-10-02.md` 卡C 节），修复方向已写好。

### A-C3 · 待移入窗内删除不取消完成计时器

- **缺陷**：`PanelModel.deleteTodo` 不清理 `completionTimers`/`pendingCompletionIDs`——1 秒待移入窗内删除待办，计时器到点对软删行调 `setCompleted(id, true)`，仓储 UPDATE 不带 `deletedAt IS NULL` 条件，**回收站里的行被静默标完成**；1 秒内撤销删除的待办会在无操作下"自己完成"。
- **主修复（UI 侧）**：`deleteTodo` 成功路径取消该 id 的计时器并从 `pendingCompletionIDs` 移除（对齐 `toggleTodoCompletion` 中取消分支的清理语义）；`deinit` 已有全量取消不动。
- **可选加固（数据层，评估后决定）**：`TodoRepository.setCompleted` 的 UPDATE 加 `AND deletedAt IS NULL`——注意它影响返回值语义（`handled`/changesCount）与通知动作路径（`setCompleted(uuid:)`），**评估涉及面后认为低风险才做**，做则同步 L1 用例 + docs/data-layer 契约句；拿不准就只做 UI 侧并记录不做理由。
- **测试**：1 秒窗内删除 → 计时器到期不写库（回收站行 completedAt 不变）；删除后撤销 → 待办保持未完成；既有 `completionDelay` 注入缩短模式复用。

### A-C4 · 面板快照缺失时主窗口编辑被静默丢弃（P2，本卡重点）

- **缺陷**：`PanelModel.saveNoteContent`（`notes.first(where: id)` 找不到即 return）与 `saveTodoTitle`（同款守卫）——面板观察流失败而主窗口流健康时（同一仓储两个独立订阅），主窗口的编辑/清空**无写入、无报错、无横幅**地被丢弃。违反产品原则 1（宁可报错不能静默丢失）。
- **修复方向（按台账）**：id 不在快照时**兜底直写仓储**——
  - `saveNoteContent`：不在快照 → trim 后空仍走 `softDelete(id)`（幂等，返回 false 即已删，静默）；非空直接 `updateContent(id, to:)`（跳过"未变跳过"检查——无快照可比；仓储对软删行也允许更新，竞态语义不变）。仓储抛 `notFound` 走既有 `report` 提示条（诚实报错优于静默丢弃）。
  - `saveTodoTitle`：不在快照 → 空标题仍回退不保存；非空直接 `updateTitle(id, to:)`，notFound 同上。
  - **不动**：快照命中时的既有路径（未变跳过、守卫）一字不改——热路径零风险。
- **连带评估（台账要求）**：快照失效=面板流失败，主窗口已有读失败反馈（W3 readFailureHandler）——确认修复后两通道文案不打架（编辑保存成功后若读失败横幅仍在，属如实状态，不改）。
- **测试**：面板快照缺 id 时 `saveNoteContent` 直写落库（断言 DB 行）；`saveTodoTitle` 同；空内容软删幂等；notFound → 横幅出现；**既有 LateDebounceGuardTests 全部不变全绿**（守卫语义未动）。
- **风险熔断**：实施中发现兜底直写与守卫/防抖/撤销栈任一语义纠缠不清，**停止此项**，台账记录原因与建议方案，只交付 C3。不许硬改。
