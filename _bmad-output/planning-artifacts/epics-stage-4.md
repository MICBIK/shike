## Overview

阶段 4 的目标（docs/02）：**朋友能从 GitHub 自助安装、收到更新；数据可以找回、可以导出。**

- 发布链路是一条龙：S4-00 验证"ad-hoc 签名 + Sparkle EdDSA"可行（ADR-032）→ S4-03 一条命令打包发布 → S4-02 应用内自动更新 → S4-04 README 安装说明。朋友侧的"下载 → 放行 → 用起来 → 收到更新"全链可用。

- 两个候补（URL Scheme、导入向导）**默认不进阶段 4**，拍板材料见文末附录 A/B。

阶段验收门槛（docs/02 原文，5 条）：从没装过拾刻的 Mac 按 README 完成首次打开；v0.5.0 → v0.5.1 检查更新升级成功且数据完整；删除内容可在"最近删除"找到并恢复；导出 Markdown 用其他编辑器打开内容完整；至少一位朋友完成安装并使用一周、反馈记录到 Issues。

作为实现发布链路的人，
我希望在写正式集成代码前验证"ad-hoc 签名 + Sparkle EdDSA"完整链路可行，

**状态：**✅ 完成（2026-10-03 夜卡A，临时原型 SparkleTestApp，零 Shike 工程改动）。结论：**可行**，记入 docs/07 **ADR-032**——macOS 27.0.1 双轮全链走通 + 篡改负向拒绝；Gatekeeper 无二次拦截；两条边界限制（静默更新时序 Sparkle 内部调度 0–60s；首次分发放行不归本链路，随 ADR-003）。

> **已回填（ADR-032，2026-10-03）：**①Gatekeeper 无二次拦截（Sparkle 下载不落 quarantine、替换后 178ms 自动重启零弹窗）——更新确认文案按常规写，S4-04 无"可能被拦"联动负担；②本机 macOS 27.0.1 双轮全通，macOS 15 口径由临时 workflow 在 GitHub runner 复跑（结论见晨报卡A 节）；③官方口径：Developer ID + 公证是 "if possible" 建议项，**EdDSA 必配**（无 EdDSA 更新已被 Sparkle 弃用）；④最小配置面：Info.plist 仅 `SUFeedURL` + `SUPublicEDKey` 两项必配，检查间隔默认即每日（86400s），`SUAutomaticallyUpdate` 控静默。两条工程细节：本地 http 测试源需 `NSAllowsLocalNetworking`（生产 https 免）；Sparkle 委托方法 2.10 有更名（`didFinishLoading`、`SPUUserUpdateState`）。

4. 更新安装后重启为新版本，用户数据完整（更新流程不触碰数据目录——数据目录与 App 目录分离是既有架构，验收显式覆盖）。
5. 菜单栏 app（无 Dock 图标）下更新窗口能正常前置与聚焦（真机验证，LSUIElement 场景）。
6. 更新控制器可注入协议以便单测（开关读写、触发路由）；Sparkle 本体不打桩。

### Story 6.4: 打包发布一条命令（S4-03）

作为发布者，
我跑一条命令就能从指定源码标签产出全套发布物并上架，
以便发布不依赖口口相传的手工步骤、朋友拿到的都是同一套产物。

**依据：**docs/02 S4-03；docs/04 §6.11（appcast 托管 `https://micbik.github.io/shike/appcast.xml`、EdDSA 私钥只在开发者钥匙串）。

> **已回填（ADR-032，2026-10-03）：**可行定案。打包链参数：`zip -qry`（保框架符号链接，`-x "*.DS_Store"`）→ `sign_update -p` 输出 `sparkle:edSignature` + `length` 写入 enclosure → appcast 的 `sparkle:version` 用 CFBundleVersion 单调整数。工具获取：无需 brew——SPM resolve 后预编译工具在 `.build/artifacts/sparkle/Sparkle/bin/`（generate_keys / sign_update / generate_appcast）；私钥经 `--ed-key-file`（文件式，配合 `SPARKLE_PRIVATE_KEY_FILE` 环境变量）或 generate_keys 钥匙串注入，**绝不入仓**。增量更新（BinaryDelta + generate_appcast）可选优化，不进首版。

**验收标准：**

1. `scripts/package.sh <tag>`（命名规格阶段定）一条命令完成：检出并编译指定 tag 的 Release → ad-hoc 签名 → 打包 zip（Sparkle 更新包）与 dmg（人工安装包）→ `sign_update` 产出 EdDSA 签名 → 生成/更新 `appcast.xml` → 用 `gh` 创建 GitHub Release 并上传产物，关联该源码标签。
2. 发布只从 tag 构建（脚本校验工作区 clean 且位于该 tag），杜绝"产物与标签不符"。
3. EdDSA 私钥只从开发者本机钥匙串读取（Sparkle `generate_keys` 体系）；脚本缺钥时明确报错退出，**任何密钥材料不入仓、不进 CI 日志、不进产物**（红线）；钥匙串的密钥备份方法写入 docs（丢失 = 已发布版本无法再推更新）。
4. `appcast.xml` 符合 Sparkle 2 格式：版本号、下载 URL（指向 GitHub Release 资产）、`sparkle:edSignature`、最低系统版本（macOS 15）、更新说明（release notes 来源建议脚本参数传入或读 `RELEASE-NOTES.md`，不依赖阶段 5 的 CHANGELOG）。
5. appcast 发布到 GitHub Pages（`gh-pages` 分支，仓库 Pages 设置随之开启——首次配置属本故事）；appcast 是公共接口，推送即生效，回滚靠再推送。
6. 重复运行幂等或给出清晰冲突提示（Release 已存在时如实报错，不静默覆盖）。
7. 真实产物在本机安装启动成功（v0.5.0），与 ADR-032 结论一致；脚本本体过 `checks.sh`（文件头等规则适用 scripts/）。

**依赖：**S4-00（链路可行性与参数）。

**文件面预估：**`scripts/package.sh`（新，主体）；`docs/06-开发规范.md` 增"发布流程"小节（含密钥备份、Pages 配置、回滚）；`.github/workflows/` 不改（发布是开发者本机动作，不做 CI 发布——若产品负责人要 CI 发布另立故事）；`gh-pages` 分支（新，只含 appcast 与 Pages 骨架）。预估 2–3 个入仓文件。

**风险与对策：**sign_update 二进制随 Sparkle SPM 在 DerivedData 里路径不稳定 → 脚本定位失败时提示用 `brew install sparkle` 的独立 CLI（规格阶段定死一种）；dmg 制作 `hdiutil` 够用但volname/布局细节需一轮真机调；GitHub Pages 首次启用有传播延迟（验收留缓冲）；发布脚本是全阶段唯一有"对外发布"副作用的故事 → 脚本对创建 Release/推 appcast 两步设 `--publish` 显式确认位，默认只构建不发布。
