> **权威契约。** 本 SPEC 与 `companions:` 中的文件，构成经过保全校验的完整契约：做什么、测什么、怎样验收。`sources:` 中的文件仅供追溯；只有需要叙述性理由时才去查阅。

# 阶段 0 · 地基（v0.0）

## Why

这项工作既是强制要求，也是一个愿景。旧项目 TZMemo 的框架代码从未编译通过，文档却标成了"完成"（ADR-001、ADR-014），所以拾刻必须从一个经过 CI 和实测验证的地基重新起步。阶段 0 不交付用户功能，交付的是阶段 1～5 共用的基础：

- 模块边界与依赖方向；
- v1 数据结构——产品负责人从阶段 1 起每天用它记录真实内容，迁移只能追加，结构上的错误会永久留下；
- "不丢数据"的安全底座；
- 以 05 为唯一来源的中文日期解析；
- 由 CI 裁决"是否完成"的流水线。

产品负责人会把后续阶段交给其他负责人，因此架构约定必须写成契约，并尽量由编译器和 CI 机械地守住，而不是靠口口相传。

## Capabilities

- **CAP-1** 仓库基础（S0-01）
  - **intent:** 任何人克隆仓库后，都能看到完整的许可证、致谢与第三方声明、构建说明和约定的目录结构，每个源文件都声明 GPL-3.0-only。
  - **success:** 仓库中有 LICENSE（GPL-3.0 原文）、NOTICE（已登记 GRDB 7.11.1、全部移植文件和 demo 基线提交）、按实测可用的 README 构建步骤，以及 .gitignore；执行 `xcodegen generate` 并构建后，`git status` 是干净的；CI 检查确认每个 `.swift`、`.sh` 文件都带标准文件头。
- **CAP-2** 工程与分层（S0-02）
  - **intent:** 开发者能从 `project.yml` 生成工程，构建出只驻留在菜单栏的 App「Shike」；它依赖本地包 ShikeKit 的 ShikeDateParser 和 ShikeData 两个库，依赖方向由机械手段守住。
  - **success:** 在 CI 的 Xcode 26 上，`xcodegen generate` 加 `xcodebuild build` 零警告通过；运行后 Dock 中没有图标；CI 检查确认 ShikeKit 没有引入 AppKit/SwiftUI、App 没有 `import GRDB`、ShikeData 以 `internal import` 引入 GRDB，两个库互不依赖。
- **CAP-3** 中文日期解析（S0-03）
  - **intent:** 待办模式将来调用的解析器，能按 05 识别中文日期和时刻、给出高亮区间、清理标题；结果与系统的区域、日历和"一周第一天"设置无关。
  - **success:** 05 §9 的每一行（A01～M08）都有同编号的自动化测试，并全部通过；05 用例表与测试数据的编号或输入不一致时，守护测试失败；CI 检查确认解析器源码不读取系统的日历和区域设置。
- **CAP-4** 数据层 v1（S0-04）
  - **intent:** App 能按 v1 结构保存便签、待办和桌面卡片，通过仓储完成全部读写，数据变化后自动收到最新结果；删除都是可以恢复的软删除。
  - **success:** L1 测试覆盖以下各项：空库迁移后的表、列、约束和索引与规格一致；uuid 以 36 位小写文本存储；04 §4.2 列出的每个仓储方法；软删除、恢复、永久删除和卡片级联；snoozedUntil 与 updatedAt 规则（ADR-017）；每次写入后观察流都推送新结果。
- **CAP-5** 写入失败可见（S0-05）
  - **intent:** 任何数据写入失败，都会带着可读的中文原因到达界面；用户的输入不丢，失败也不会被吞掉。
  - **success:**
    - L1 测试证明：写入失败时抛出分类错误（例如只读库），不存在"失败却返回成功"的路径；开启模拟写入失败后，所有仓储写方法都得到 `writeFailed(.simulated)`。
    - L2 测试证明：PanelModel 能把错误变成红色提示条"保存失败：原因"，并附"重试"。
    - 仓储写操作没有使用 `try?` 的地方。
    - 带 `-ShikeSimulateWriteFailure YES` 启动时，写操作会失败，供阶段 1 起的验收使用。
- **CAP-6** 数据库打不开时的明确提示（S0-05）
  - **intent:** 启动时如果数据库打不开（目录不可用、文件损坏、迁移失败、文件来自更新的版本），用户会得到明确的提示，并可以选择重试、打开数据目录或退出；App 绝不改用内存库或新建空库。
  - **success:**
    - 带 `-ShikeSimulateDatabaseOpenFailure YES` 启动时，弹出"拾刻无法打开数据文件"、原因和三个按钮。
    - "打开数据目录"会在访达中打开目录，然后回到提示；"重试"成功后正常启动；"退出"会退出 App。
    - L1 测试证明：损坏的文件和来自更新版本的库分别得到对应的失败原因，且原文件不变。
- **CAP-7** 每日自动备份（S0-05）
  - **intent:** App 在每个本地自然日自动保留一份数据库备份，只保留最近 7 份，既不阻塞启动，也不打扰用户。
  - **success:**
    - 运行一次后，数据目录的 `Backups/` 中有 `shike-当天日期.sqlite`，能打开，且数据与主库一致。
    - L1 测试覆盖：当天已有备份时跳过；超过 7 份时删除最旧的；忽略无关文件；中途失败不留下半成品。
    - 备份失败只写日志。
- **CAP-8** 菜单栏图标与面板（S0-06）
  - **intent:** 用户能在菜单栏看到拾刻图标，左键开关面板；面板中能切换「便签｜待办」并看到对应的空状态，点击面板外部即收起。
  - **success:** 验收清单第 3、4 条实测通过；面板打开后成为关键窗口；连续快速点击图标，不会出现"刚关上又弹开"。
- **CAP-9** 右键菜单与主菜单（S0-06）
  - **intent:** 用户右键点击图标，可以打开设置、查看关于、退出拾刻；即使没有可见的菜单栏，标准编辑快捷键以及 ⌘,、⌘Q 也能使用。
  - **success:** 验收清单第 5 条实测通过；L2 测试确认隐藏主菜单包含"设置… ⌘,""退出拾刻 ⌘Q"，以及撤销、重做、剪切、复制、粘贴、全选，并使用标准的选择器和快捷键。
- **CAP-10** 设置窗口骨架与关于页（S0-06）
  - **intent:** 用户能打开唯一的设置窗口，看到通用、快捷键、提醒、卡片、数据、关于六个分页；还没实现的分页会注明将在哪个阶段提供。关于页显示版本、许可证、源码链接、致谢，以及 GPL 要求的法律声明，并能离线查看许可证全文。
  - **success:**
    - 从右键菜单"设置…"或按 ⌘, 打开时，窗口在最前面，且只有一个实例；"关于拾刻"直接打开关于分页。
    - 关于页显示"0.0.0（1）"、版权声明、无担保声明、"可以依据 GPL-3.0 再分发和修改"，以及 <https://github.com/MICBIK/shike>。
    - "查看许可证"在断网时也能显示随 App 打包的 LICENSE（GPL-3.0 全文）。
    - 五个占位分页显示正确的阶段号。
- **CAP-11** 组装点与可测试的启动（S0-02、S0-06）
  - **intent:** 后续负责人能在唯一的组装点接入新的服务、窗口和模型；测试和手工验收都能与真实数据隔离。
  - **success:**
    - L2 测试用内存库和独立的 UserDefaults 组装 AppEnvironment，并驱动 PanelModel。
    - 运行 L2 测试时，不创建数据目录，不写入真实的偏好设置，不出现菜单栏图标。
    - 带 `-ShikeDataDirectory <路径>` 启动时，数据库和备份都落在指定的目录中。
    - 除 AppEnvironment 外，代码中没有全局单例。
- **CAP-12** CI（S0-07）
  - **intent:** 每次推送和发起 PR 时，自动运行包测试、构建 App、运行 App 层测试以及架构与合规检查；main 只接受检查通过的合并。
  - **success:**
    - 推送后，GitHub Actions 显示 `checks`、`package-tests`、`app` 三项。
    - 测试失败、新增警告或检查违规，任何一种都会让 CI 变红。
    - main 的分支保护要求这三项通过。
    - main 上的 CI 显示通过（验收第 1 条）。
- **CAP-13** 架构交接（为后续负责人新增）
  - **intent:** 后续负责人只读 docs/，就能按统一的方式扩展拾刻：新增仓储方法、偏好键、设置分页、界面文案、服务、调试参数、移植文件和数据库迁移。
  - **success:**
    - 阶段 0 收尾时，04 已写回本规格确定并经实现验证的契约，并有一节"扩展指南"，逐项给出步骤和示例位置。
    - 07 为重大取舍新增了 ADR。
    - 06、NOTICE、README、CLAUDE.md 中的命令和事实都与 CI 实测一致。
- **CAP-14** 迁移前备份（S0-05 的延伸）
  - **intent:** 对已有的数据库执行新的迁移之前，先自动留一份备份；备份失败时不迁移。
  - **success:** L1 测试用一个 v1 库和一个测试专用的 v2 迁移验证：迁移前 `Backups/` 中已经有 `shike-before-v2-日期.sqlite`，内容是迁移前的；备份失败时得到 `openFailed`，库没有被迁移；新建的空库不做这种备份。

## Constraints

- **工具链：**
  - 最低 macOS 15；Swift 6 语言模式，严格并发检查；Xcode 26 或更高版本。
  - CI 使用 `macos-26` 镜像的默认 Xcode（2026-09 时为 26.6）。本地 Xcode 27 比它新，两者不一致时以 CI 为准。
  - ShikeKit 的 `swift-tools-version` 为 6.2。
- **模块边界：**
  - App 依赖 ShikeData 和 ShikeDateParser，这两个库互不依赖。
  - ShikeKit 不引入 AppKit/SwiftUI；ShikeDateParser 只依赖 Foundation。
  - 界面代码不直接访问数据库：ShikeData 以 `internal import GRDB` 引入 GRDB，公开 API 中不出现任何 GRDB 类型，App 不 `import GRDB`。
- **生命周期：**
  - 使用 `main.swift` 加 `AppDelegate`，不使用 SwiftUI 的 App/Scene。
  - 窗口由 AppKit 管理，窗口内容用 SwiftUI。
  - `LSUIElement = YES`；必须有隐藏的主菜单（04 §6.1）。
- **不丢数据：**
  - 不静默吞掉错误；写入和文件操作的失败不得用 `try?` 丢弃。保存失败时保留输入。
  - 数据库打不开时，绝不改用内存库或新建空库，也不删除、不覆盖原文件。
  - 执行新的迁移之前必须先备份（ADR-018）。
  - 禁用 GRDB 的 `eraseDatabaseOnSchemaChange`，开发期也不行。
- **数据结构：**
  - v1 以 04 §5 和 data-layer.md 为准；迁移只追加，已发布的迁移永不修改。
  - uuid 以小写文本存储，由测试守护。
  - 所有时间戳都来自可注入的时钟。
  - updatedAt 只在内容类变化时更新（ADR-017）。
- **组装：**AppEnvironment 是唯一的组装点；除它之外不使用全局单例，移植代码中的 `shared` 一律去掉；依赖都通过初始化参数注入。
- **依赖：**
  - 一律锁定精确版本；阶段 0 只新增 GRDB 7.11.1（MIT）。
  - CI 中 XcodeGen 固定为 2.46.0，并校验 SHA-256。
- **GPL-3.0-only：**每个 `.swift`、`.sh` 文件都带标准文件头；凡是照搬或改写 demo 的文件，都要加上来源和修改说明，并登记到 NOTICE 和 04 §7。
- **测试：**不依赖真实的当前时间和系统时区：基准时间 T0 = 2026-09-23 12:00，时区 Asia/Shanghai。能用 L1 覆盖的，不留给 L2/L3。
- **集中定义：**界面文案只放在 `Localizable.xcstrings` 中（开发语言 zh-Hans）；偏好键只在 `Preferences.Key` 中定义；调试启动参数只在 `LaunchOptions` 中定义。
- **隐私：**没有遥测；阶段 0 没有任何网络访问；日志不记录便签和待办的内容。
- **最小化：**只创建阶段 0 用到的目录、类型和偏好键（04 §2）；不新增编译警告，由 CI 以"警告即错误"的方式执行。

## Non-goals

- 阶段 1～5 的任何能力：
  - 输入与编辑：快速输入框、列表行与编辑、删除与撤销、全局快捷键、Esc、按键缓冲、搜索、时间识别界面。
  - 面板与菜单：调整并记住面板尺寸、"打开拾刻"菜单项、⋯ 菜单。
  - 提醒：通知与提醒调度、待办分组、菜单栏计数。
  - 其他功能：开机自启、桌面卡片界面、最近删除、导出。
  - 设置与发布：设置各分页的具体内容（关于页除外）、自动更新、打包发布、首次启动引导、正式图标。

  各组件的分界见 scope-boundaries.md。
- 后续阶段的领域逻辑：待办分组（S2-06）、提醒计划（S2-05）、搜索转义（S2-09）、最近删除的自动清理（S4-05）、菜单栏计数查询（S2-08）。
- 05 以外的说法：05 §8 列为暂不支持的说法，以及旧解析器支持但 05 没有列出的说法（如"当天"），一律不识别。修订 05 §7 的标题清理顺序不在本阶段（Issue #2，在 S2-02 之前决定）。
- 单实例限制（Issue #1）。
- 第三方许可证全文随 App 打包：暂缓，等项目全部完工时由产品负责人再定。注意阶段 4（S4-03）起就开始分发安装包，而 MIT 要求随二进制附带 GRDB 的版权与许可声明。
- 发布：不做 Release 打包、分发签名和更新；阶段 0 只在 main 上打 `v0.0.0` 标签。
- TZMemo 的数据和界面代码：不迁移（本来就没有真实数据），只迁入解析器。
- App Sandbox 和 Hardened Runtime：不启用（ADR-011）。
- 性能预算的测量（S5-05）：阶段 0 只保证启动路径上不做同步的重活。

## Success signal

- 在打了 `v0.0.0` 标签的 main 提交上：
  - GitHub CI 的三项检查全部通过，覆盖 05 的全部用例、数据层与备份测试、App 构建与 L2 测试、架构与合规检查；
  - 产品负责人按 02 中阶段 0 的 7 条验收清单逐条实测通过。
- 阶段 1 的第一个故事不需要改动工程结构、模块边界或 v1 表结构，就能开工。
