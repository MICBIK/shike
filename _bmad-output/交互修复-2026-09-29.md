# 桌面卡片交互修复台账（2026-09-29 白天，ADR-026）

## 用户反馈（原话要点）

> 悬浮卡片的交互方式存在严重的问题，非常的反人类。贴在桌面层之后完全没法点击，卡片上连取消都点不了；常用功能应该做到卡片顶部工具栏里；显示内容要和工具栏有间距，工具栏隐藏还是显示都不能出现遮挡；还有很多问题需要打磨，特别是交互；不知道怎么做就去分析同类项目的做法。

阶段 3 分支（stage-3/desktop-cards）尚未合并——交互硬伤在合并前被真机预验收拦下，流程起效。

## 根因（三处叠加）

| # | 根因 | 证据 |
|---|---|---|
| 1 | **桌面层级取错**：desktopWindow 层（key=2，-2147483623，壁纸层）。Finder 整屏桌面窗口在 desktopIcon 层（比壁纸高 20），窗口服务器把点击给"光标下可收事件的最高层"——desktopWindow 层必然点不到。S3-00 只目视了"沉到全部窗口之下"，没验证点击投递 | Electron 官方文档"desktop window will not receive focus, keyboard or mouse events"；CGWindowLevel.h |
| 2 | **工具栏依赖悬停**：顶部操作条是 hover 浮现的覆盖层，正文顶部留白在 10↔26pt 跳动；所有按钮要 hover 才可点 | StickyCardPanel 旧实现 |
| 3 | **常用功能入口弱 + 承诺未兑现**：编辑只有双击（不可见）与 ⋯ 菜单；§10.2 承诺的"拖边缘或角调整大小"未实现（clampedResize 零调用方） | 代码审计 |

## 修复（commit c4e3d32，ADR-026）

1. 桌面层级 → `CGWindowLevelForKey(.desktopIconWindow) + 1`（壁纸之上、图标之上、低于普通窗口；原值与 Finder 同层 z 序不可预期，同类 Tack +1 / macterm +2 均不停原值）。
2. 工具栏常驻：永远占位（正文固定从其下 2pt 开始，不遮挡不跳动）、永远可点（不依赖 hover）；hover 只把按钮组 55%→100% 提亮。
3. 常用功能上栏：编辑（铅笔/✓）、颜色（按钮即当前色板）、层级（显式菜单三选，图标随层级 pin/macwindow/square.stack.3d.up）；循环按钮与 `CardTheme.nextLevel`、`Actions.cycleLevel` 下线。
4. 右下角调整大小把手（补齐 §10.2）：实时钳制最小 160×100，松手按可见区域钳制并持久化；busy 与拖动同路（调整大小中不自动隐藏）。
5. 正文右键 = ⋯ 菜单同源（只挂展示态，保留编辑态 TextEditor 原生菜单）。
6. 防御配套：`.stationary` + `.ignoresCycle`；`CardHostingView.acceptsFirstMouse` 兜底；换层级 `orderFrontRegardless` 仅在窗口可见时执行（"隐藏所有卡片"期间观察流回流不得复活已收起的卡片）。

## 调研摘要（同类产品做法，14 个来源）

- **桌面层窗口**：窗口服务器点击路由给"光标下可收事件的最高层"；Finder 桌面窗口整屏覆盖 desktopIcon 层，desktopWindow 层（及以下）必然收不到点击。可交互贴桌窗口的业界取值：**desktopIconWindow+1**（Tack，SwiftUI 便签同构）/+2（macterm）；Übersicht 非交互 widget 就在 desktopWindow 层且显式 ignoresMouseEvents（明知收不到），交互 widget 临时升 normal−1。副作用：卡片挡住正下方桌面图标的点击——同类一致，拖开即可。
- **工具栏范式**：Windows 11 Sticky Notes = 常驻顶条（布局的一部分，不遮正文）；macOS Stickies 无卡片内工具栏（全走菜单栏）；Tack = 常驻细标题条 + 悬停浮现的角落按钮（opacity + allowsHitTesting 同步门控）。防遮挡正统做法：预留布局空间（本方案采用）。顶层按钮收敛集合：✕ 关闭、pin/层级、颜色/外观；低频进 ⋯。✕=只隐藏不删（三家共同约定，拾刻 ✕=取消钉住便签保留 ✓）；自动保存全静默。
- **非激活面板**：nonactivatingPanel 必须在初始化时定死 styleMask；≤macOS 14 的 SwiftUI plain 按钮在非激活窗口首击被吞（acceptsFirstMouse 兜底，15+ 已修）；onHover 走 NSTrackingArea 不需要 key 状态（自建时必须 .activeAlways）；ignoresMouseEvents 隐藏态靠全局轮询 NSEvent.mouseLocation 唤回是社区标准模式（零权限、鼠标静止也生效）。

来源：jameshfisher.com（窗口层级排序）、CGWindowLevel.h（SDK 头文件）、electronjs.org/docs（desktop 层不收输入）、electron#12073、uebersicht UBWindow.m 与 issue#97、Tack NoteWindowController/NoteRootView、macterm NativeDesktopWidgets、Apple Stickies 帮助、SideNotes 官网、philz.blog（NSPanel nonactivating）、christiantietze.de（非激活窗口按钮首击）、levelup.gitconnected（mouseLocation 轮询唤回）、developer.apple.com（NSTrackingArea/addGlobalMonitorForEvents）。

## 补记（同日午后）：拖动后改选项弹回初始位置 + 阶段 3.5 开工

**用户反馈 2：**卡片拖到新位置后，但凡改颜色或其他选项，卡片弹回屏幕居中的初始位置。**另提醒：⌥N 不需要每次构建后重新授权，只在真失灵时才重开授权（已记入记忆并修正 ADR-021 相关描述）。**

**根因（ADR-027）：**`controller.apply` 把观察流快照里的 frame `setFrame` 回窗口，而拖动落库是异步写——任何其他写库（改选项正是）在拖动写提交前触发观察流回流，旧 frame 就把刚拖的位置弹回去。仓储层 `updateFrame`/`updateOptions` 本来各写各列互不覆盖（回归测试锁定），frame 的 DB 写入者只有窗口层自己——apply 的回写是只带竞态的冗余通路。

**修复（4017906，CI success）：**frame 单向写——apply 不再回写窗口位置，DB frame 只在创建控制器时消费；位移持久化收敛于 dragEnded/resizeEnded，`windowDidMove` 兜底（手势收尾丢失也落库），`lastPersistedFrame` 去重。PinCardFlowTests 新增"移动与改选项互不覆盖"回归（169 测试全绿）。

**阶段 3.5 开工（5edbf5b + P1 453b60e）：**docs/03 §16 主窗口交互设计 + epics-stage-3.5.md 六故事拆解（5.1 骨架 → 5.2 左栏 → 5.3 便签 → 5.4 待办 → 5.5 回收站（需 ShikeData observeDeleted）→ 5.6 导出）。**S3.5-01/02 已实现**：主窗口单例（右键菜单+设置-通用打开、前置聚焦、frameAutosave 记尺寸、关闭仍驻留菜单栏）、左栏三入口选中态记忆、未实现视图诚实占位。

**打磨 P1（453b60e）：**主窗口 `isReleasedWhenClosed` 置 false——程序化 NSWindow 默认 close-即-release，控制器强持有下 ARC 过释放，关窗有崩溃风险。

## 补记 2（同日晚些）：普通层级形同置顶修复（ADR-028）

**用户反馈 3：**"窗口不管选悬浮、普通还是桌面，都会在顶层。选普通窗口，卡片还压在浏览器上，和浮在最上层一样。"

**根因：**ADR-026 决策 5 的误判修复——当时把"切回普通层后卡片沉到其他窗口后面"（**普通层级的正确语义**，03 §10.3"和其他窗口一样会被遮挡"）当成 bug，加了"换层级后 orderFrontRegardless"。此后每次设置回流（改选项/内容/位移落库）都把卡片提到层级最前，普通层级失效形同置顶。

**修复（5445284）：**`apply(options:)` 只设 level（setter 自动挪到新层正确位置），删 orderFrontRegardless；`show()`（新建/恢复/全部显示等用户主动行为）保留；顺带修 `windowDidMove` 在拖动中连续触发的写库风暴（isDragging 时跳过，收尾统一落库）。CardGeometryTests 新增层级映射断言（floating > normal=0 > desktop > desktopIcon），170 测试全绿。

**验收追加 1 项：**卡片选"普通窗口"后，激活浏览器时卡片被浏览器遮挡（不再压在浏览器上）；切回"浮在最上层"立即浮出。

## 补记 3（同日更晚）：普通层级完整语义（ADR-029，原型取证）

**用户反馈 4：**ADR-028 构建上"还是没修好"——普通层级卡片仍压在浏览器上。

**取证（Prototypes/LevelProbe，swiftc 直编 + CGWindowList）：**v2 同进程矩阵：激活普通窗口能压住全部配置的 panel；v4 跨 app 矩阵（TextEdit 激活，三跑稳定）：TextEdit 压住 nonactivatingPanel 全部 collectionBehavior 组合——**z 序机制正常，原型无法复现**。真实机制：level setter 把窗口放到新层**最前**，切到"普通"的瞬间卡片正好压住正在用的浏览器；用户不重新激活浏览器就一直"看起来置顶"。ADR-028 只删对了强提，没解决"切换即层内最前"。

**修复（c06926a）：**按 03 §10.3 完整语义实现——①切到"普通"立即 orderBack 让位（沉到普通窗口链底部，桌面可见部分仍在）；②点击卡片可见部分 orderFront 浮到前面（规格"点击后浮到前面"）；③启动恢复的普通层级卡片同样让位（恢复首帧标记，用户主动新钉不让）；④floating/desktop 行为不变。

**验收（三步闭环）：**切普通 → 卡片立即让位（不压浏览器）→ 点卡片可见部分 → 浮到前面 → 激活浏览器 → 又被压回。
