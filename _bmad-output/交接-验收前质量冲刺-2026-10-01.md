## 2. 工作项详单

### W1 · 退出冲刷同步化（P0）

**现状证据（动手前先重读这些位置）：**

- `Shike/Panel/PanelModel.swift:611-627` `endEditingIfNeeded()`：结束编辑后 `Task { await saveNoteContent(id, text) }`——fire-and-forget。
- `Shike/MainWindow/MainWindowController.swift:263-268`：注释自认"写入本身是 fire-and-forget Task……弱保证"。
- 接线层再包一层 Task：`MainWindowController.swift:154-156`（`Task { await panelModel?.saveNoteContent }`）。
- `Shike/Cards/CardManager.swift` `endEditing(save:)`（约 :468）同样是异步写路径；关闭卡片有冲刷（:503/:541），**退出路径没有**。
- `Shike/App/AppDelegate.swift:347-359` `applicationWillTerminate`：endEditing 之后进程随即退出，上述 Task 未必执行完。

**风险场景**：编辑便签/待办标题/卡片正文 → 立即 ⌘Q → 最后一次编辑丢失。违反产品原则 1（不丢数据）。

**范围界定**：快速输入框草稿已持久化（Preferences）不必管；提交中的创建动作也安全（草稿只在成功后清空，进程被杀则草稿仍在）。要修的只有**编辑态**：面板行便签/待办标题、主窗口便签行、卡片正文，以及各防抖窗内的待存文字。

**方案（推荐，可按实际代码微调）：**

1. 新建 `Shike/Support/SyncFlush.swift`：`enum SyncFlush { static func perform(_ work: …, timeout: Duration) }`——用 `Task.detached` 包裹异步写 + `DispatchSemaphore.wait(timeout:)` 同步等待，超时放弃并 `Log.app.error`。
   - **死锁警告（必须遵守）**：不能用 `Task { }`——它继承 `@MainActor` 隔离，主线程被信号量阻塞时任务永远不会启动，直接死锁。必须 `Task.detached`（脱离 actor 继承）；仓储 `NoteRepository` 等是 `Sendable` struct，detached 调用安全。
   - 超时给 3 秒；退出场景无 UI 可报，日志即底线（晨报里说明这一取舍）。
2. `PanelModel` 增加 `flushPendingEditsSynchronously()`：读 `editingNoteID/Text`、`editingTodoID/Text`，按 `saveNoteContent`/`saveTodoTitle` 的既有数据语义（trim、空→softDelete、内容未变跳过）直接经仓储同步执行。既有异步路径不动（UI 时机照旧），本方法退出专用。
3. `MainNotesModel` 暴露在编辑内容快照接缝；`MainWindowController.endEditingIfNeeded()` 改为捕获后同步冲刷（同语义：空→软删除、未变跳过）。
4. `CardManager` 退出路径补同步冲刷（`applicationWillTerminate` 或 `stop()` 里先 `endEditing(save: true)` 再同步等待落库）。
5. `applicationWillTerminate` 中**冲刷必须在各 stop() 之前**执行。

**测试（L2）**：内存库构造编辑态 → 调同步冲刷 → **不 await 任何 Task** 直接断言数据库行已更新；空内容→软删除；内容未变→updatedAt 不动；注入慢仓储 + 短 timeout 断言不会永久阻塞。

**真机验收（明早）**：编辑便签后立即 ⌘Q，重开内容在。

### W2 · 主窗口三视图首帧空态闪现（P1）

**现状**：`MainNotesView.swift:238`、`MainTodosView.swift:225`、`TrashView.swift:292` 都以 `isEmpty` 分流空态——观察流首帧未到时模型为空数组，先闪一帧"还没有便签 / 没有待办 / 回收站为空"再跳回内容。面板不受此困扰（呼出时首帧早已送达），范围只做主窗口三视图。

**方案**：`MainNotesModel` / `MainTodosModel` / `TrashModel` 各加 `private(set) var isLoaded = false`，收到首帧（含空数组帧）置 true；流失败/非取消结束时也置 true（失败由 W3 的反馈条承接，不能停在假空态）。视图空态分支改为 `isLoaded && isEmpty`，未加载时渲染空白纸感底（不要放 ProgressView，半秒的转圈比空白更吵）。

**测试（L2）**：三模型各一条——首帧前 false → 首帧后 true；失败路径同样翻转。

### W3 · 主窗口统一反馈：写失败与读失败可见（P1）

**现状**：

- 主窗口编辑保存失败 → `panelModel.report` → **面板**提示条；面板收着时用户在主窗口完全无感。
- 主窗口观察流失败只 `Log.app.error`（`MainNotesView.swift:119-124`、`MainTodosView.swift:122-126`）。
- 主窗口底部反馈条现状借用 `trashModel.statusMessage`（`MainWindowController.swift:94-109`），只有导出/回收站在用。

**方案**：

1. 新建 `MainFeedbackModel`（`@Observable`，message + token 自清机制，参照 `TrashModel.showStatus` 的 3 秒自清），`MainWindowController` 持有；`MainRootView` 的 `safeAreaInset` 改接它，导出成功/失败、回收站失败文案全部改写它（回收站分区内部的同源展示照旧）。
2. **写失败旁路**：`PanelModel.report` 增加 `@ObservationIgnored var writeFailureHandler: (ShikeDataError) -> Void = { _ in }`，`writeFailed` 分支里调用；`MainWindowController` 接线为"主窗口可见时显示失败文案"。面板横幅保留不动——哪个窗口看得到就在哪个窗口有反馈，不算重复打扰。
3. **读失败**：`MainNotesModel`/`MainTodosModel`/`TrashModel` 的流失败分支经注入闭包上报到 `MainFeedbackModel`（文案如"数据读取失败"，键新增到 `Localizable.xcstrings`，注意符号生成 + 键序 + 红线 12）。
4. 失败反馈不自动清除比 3 秒更稳妥？——**按 3 秒自清 + Log 留痕即可**，与现有通道一致；编辑内容仍在输入框不丢（原则 1 靠 W1+W5+既有防抖兜底）。

**测试（L2）**：接线表扩用例——`simulateWriteFailure` 路径主窗口反馈出现（真机可用 `-ShikeSimulateWriteFailure` 启动参数，`AppDelegate.swift:388` 已支持）；读失败回调触发反馈；3 秒自清。

### W5 · 导出 formatter 复用（P2，S5-05 预备）

**现状**（`Shike/Services/ExportService.swift`）：markdown 路径 `headerDate`/`dateTimeText`/`dateOnlyText`（:131/:140/:149）每次调用 new `DateFormatter`——千条待办导出即千次级构造；JSON 路径 `.custom` 闭包内**每个日期** new `ISO8601DateFormatter`（:194）。

**方案**：

- markdown：三个 formatter 在 `markdown()` 入口创建一次、作参数下传私有函数；不引入共享可变状态（时区是导出级常量）。
- JSON：`DateFormatter`/`ISO8601DateFormatter` 在现代 macOS 上线程安全（Apple 文档），`json()` 顶部创建一次、闭包内引用；若 Swift 6 报 `@Sendable` 捕获错，用 `nonisolated(unsafe) private static let` 共享实例并注释线程安全依据（既有 `makeISO8601Milliseconds()` 测试工厂可提为共享来源）。
- `MainWindowController.fileDate` 每导出只调一次，保持现状。

**测试**：现有 `ExportServiceTests` 全绿（行为不变、输出逐字节一致）；可选拿千条构造数据在本地跑一次导出记耗时入晨报（**不要**把耗时断言进 CI，防抖动）。

### W4 · 同一条便签的三面编辑互斥（P1 压轴；独立提交，可整体裁剪）

**现状**：`PanelModel.editingNoteID`（面板行）、`MainNotesModel.editingNoteID`（主窗口行）、`StickyCardModel.isEditing`（卡片）互不知情；同一条便签三处可同时进入编辑，先保存方的文字被后保存方静默覆盖。docs/03 §16.7:318 的"无锁：后保存者覆盖"是**数据层契约，保留**；本项只在 UI 层防两处同时输入。

**方案（"后来者拿走"，不弹窗不拒绝）**：

1. 新建 `@MainActor final class EditArbiter`（App 环境级单份，由 AppDelegate 装配注入，不做全局单例——checks 作业禁全局单例）：按 noteID 记当前编辑 owner（`.panel/.mainWindow/.card`）及该 owner 的"结束编辑"闭包。
2. 三个编辑入口改为先 claim：目标便签已被其他 owner 编辑时，先调用对方注册的结束闭包（面板 `endEditingIfNeeded`、`MainNotesModel.endEditing`、卡片 `endEditing(save: true)`，触发即保存），再授权给新 owner。用户体验 = 点了哪里哪里拿到编辑。
3. **per-note 粒度**：不同便签各编辑各的，互不干扰。
4. 待办只有面板一个编辑面（主窗口"编辑"本来就是呼出面板定位，天然互斥），不纳入。

**测试（L2）**：arbiter 单测（claim/换主/旧 owner 闭包被调）；接线冒烟（面板进入编辑 → 主窗口 beginEditing 同一条 → 面板编辑态已收）。

**风险控制**：放最后做；实现中发现侵入面超预期（比如面板行入口散在视图层收不拢），**降级**为只做 主窗口↔面板 互斥、卡片互斥记 GitHub Issues（idea 标签），晨报说明裁剪决定。
